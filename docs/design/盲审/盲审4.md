我按软件工程设计角度评审，结论偏反方：**v0.2 的方向正确，但下一步不该马上做完整例句 CDN 化，而应先把发布链路变成可验证、可回滚、可审计的最小系统。**

## Q1：A.4 哪个判断错了 / 漏了什么？

A.4 的 5 个问题大体都成立，尤其是“例句文本更新必须发 APK”和“音频走远端、文本走 bundle 的不对称”是实质架构债。文档明确说明学习页例句来自 bundled JSON，不来自 cloud API，而音频通过 API/CDN 拉取，这会让文本和音频的发布节奏天然错位。

我认为漏掉的更严重问题是：**内容发布缺少“原子版本边界”**。现在讨论了 manifest、checksum、GC、fallback，但没有把“一个内容版本是否完整可用”定义成可验证的 release unit。例如 examples package v5、audio_assets vN、wordbook membership、content_manifest active 状态之间如果半成功，会出现：

* App 拿到新例句，但对应音频还没 ready；
* manifest active 了，但 CDN 文件未上传完整；
* 英文改动生成新 stable_id，但旧收藏、旧音频、旧包之间的过渡关系不可观测；
* GC 判断基于 current active，但客户端可能还停留在旧 content package。

所以真正的风险不是“发不发 APK”，而是**静态内容一旦 CDN 化，发布失败从构建期问题变成运行期问题**。

## Q2：是否删掉 `example_book_memberships`？

选 **C：保留 schema 设计，但不立即建表**。

我同意当前不建表。MVP、solo、无真实用户阶段，先让 `examples.word_id` 单挂足够，文档也说当前没有“按词书分例句”的产品需求，且加 M:N 会让读路径、运营生产、migration/API/测试都多一层复杂度。

但我不同意把它完全从长期模型里删除。更稳的做法是：主文档里保留 future extension contract，例如：

```txt
examples 仍是全局例句池；
未来如需按词书精选/排序/隐藏，再加 example_book_memberships；
当前包导出时按 word_book_memberships 找词，再取 examples.word_id。
```

这样既不提前付实现成本，也不让未来读者误以为“例句永远只属于 word”。

## Q3：Phase 1 + 2 合并是否合理？

选 **B：应分开，但不是拆回原来的 Phase 1**。

原文说 memberships 已完成，所以单独 Phase 1 没产出，这点成立；但把 DB migration、manifest API、pipeline、mobile downloader、checksum、drift v12、fallback、导入测试全塞进一个 Phase 1+2，会造成 PR 风险过大。文档列出的 Phase 1+2 目标横跨后端、CDN、移动端本地库、发布管线和测试。

我建议重新拆成两个可上线单元：

1. **Phase 1：发布侧只读化**
   建 `build-examples-package`、`publish-manifest`、checksum、dry-run validate，但 App 暂不消费。

2. **Phase 2：客户端消费 manifest**
   Drift 表、下载、校验、导入、fallback、学习页读取验证。

这样第一阶段不会改变用户路径，却能先证明“PG → package → manifest → CDN”这条链路可靠。

## Q4：下一周优先动哪一件？

选 **A：Phase 0.5 管线收口**。

理由：当前真正拖累后续工作的不是 5.6MB JSON，而是发布链路不可重复、不可审计、不可 GC；文档已列出现在有 4 个脚本、8 步人工流程和 6932 个 stale MP3，这说明系统还没到适合扩大 manifest 消费面的稳定程度。

但我会把 A 做成“发布系统地基”，不是简单合脚本：

```txt
第 1 天：统一 pipeline.py 入口 + README
第 2 天：validate 子命令，检查 stable_id/audio_id/source_text_hash/checksum
第 3 天：gc-stale dry-run + 删除报告
第 4 天：build-examples-package dry-run，只产物不切客户端
第 5 天：把一次完整发布流程跑通并固化测试
```

## Q5：长期 5 年视角的根本性误区

最大的盲点是：**把“内容系统”当成静态资源分发问题，而不是内容治理问题**。

5 年项目里，例句不是简单 JSON 行。它会涉及：

* 内容来源与生成器版本；
* 审核状态；
* 版权/敏感内容；
* 质量评分；
* 废弃原因；
* 多语言翻译版本；
* A/B 或难度分层；
* 用户收藏、学习历史对 stable_id 的依赖；
* 线上回滚与灰度。

所以 v0.2 现在最该补的不是 `example_book_memberships`，而是给 `examples` / `content_manifest` / pipeline 增加**内容发布治理字段和 release contract**。例如 release_id、generated_by、approved_by、status、rollback_to、manifest activation transaction、package compatibility matrix。

最终建议：**先不要冲完整 CDN 化客户端改造；先把内容发布系统做成可重复、可验证、可回滚。**这比“文本不发版更新”更基础。
