基于上传文档本身读完后的软件工程设计评审如下。整体判断：**v0.2 方向正确，但当前方案把“内容分发架构”推进得有点快；更紧急的是先把内容生产/发布链路做成可重复、可回滚、可审计的工程系统。**

## Q1：A.4 哪个判断错了？漏了什么？

我认为 **问题 4 的严重性被高估了**。例句 100% 可见、音频只有 22.3%，UI 隐藏无音频喇叭按钮，这更像内容生产进度问题，不是架构缺陷。文档也明确音频失败不阻断学习，学习页本地展示例句即可。 

更严重的遗漏是：**内容包导入的原子性与回滚语义不够明确**。方案有 checksum、manifest、`content_package_state`，但没有说清楚客户端导入 examples 包时是“先写临时表，校验完整后 swap”，还是边解包边覆盖正式表。若中途崩溃，学习页可能读到半新半旧数据。既然目标是“内容缺失不影响学习”，那包导入也必须是事务边界清晰的：下载、校验、导入临时表、完整性检查、切换 active version、清旧版本，应是一个状态机。

## Q2：是否删除 `example_book_memberships`？

选 **C：保留 schema 设计，但不立即建表**。

我同意现在不建表。当前文档说没有“按词书分例句”的产品需求，加表会增加 JOIN、运营决策和测试成本，这个判断成立。

但我不同意把它简单归为 YAGNI 后淡化。CET-4、IELTS、高中词书的例句难度差异很可能是真需求。建议在主设计中保留扩展点：`examples` 当前仍挂 `word_id`，但 examples package 的导出逻辑应允许未来从 `example_book_memberships` 或 `example_audience_rules` 切换，不要把“一个词所有词书共用同一批例句”写死进客户端查询假设。

## Q3：Phase 1 + Phase 2 合并是否合理？

选 **B：应分开，但不是恢复旧 Phase 1**。

memberships 已完成，单独做旧 Phase 1 没意义，这点文档说得对。 但 Phase 1+2 的范围太大：DB migration、pipeline、manifest API、mobile drift schema、下载校验、解包导入、fallback、测试都在一个交付单元里。

我建议拆成两个 PR：

1. **Server/package-only PR**：生成 examples package、写 manifest、可 dry-run、可回滚，但 mobile 不消费。
2. **Mobile consumption PR**：`content_package_state`、下载、校验、导入、fallback、学习页验证。

这样风险边界更清晰，也方便你在没有真实用户的 MVP 阶段逐步验证。

## Q4：下一周单选推荐

选 **A：Phase 0.5 管线收口**。

理由：当前最确定的工程债不是 CDN 化，而是内容生产链路不可重复、脚本分散、stale 资产无治理；文档已说明现在有 4 个脚本、一次新增例句要 8 步，而且已有 6932 个 stale MP3。  Phase 0.5 半天可完成单入口、README、GC dry-run，收益确定、风险低，并且是后续 CDN 化的地基。

## Q5：根本性误区

最大误区是：**把“内容分发形态”当成核心问题，而不是把“内容版本治理”当成核心问题。**

无论例句是 bundled JSON、CDN package、API，真正长期会出事故的是这些问题：哪个版本可发布、哪个版本可回滚、客户端当前读哪个版本、半包导入如何恢复、英文变更如何联动音频废弃、中文修订如何只更新文本、旧客户端 grace window 如何保证。文档已经有 stable_id、manifest、status、grace window 的雏形，但还没把它提升成统一的“内容发布状态机”。

我的结论：**先做 Phase 0.5；然后把 Phase 1+2 改成“内容版本治理 + examples package v1”的窄切口，不要同时追求 APK 减小、完整 CDN 化和 enrichment 迁移。**
