但有两个 DB 必修正项：

第一，example_sentences 现在不具备幂等安全。
plan 里说 WordbookLoader 所有插入都用 InsertMode.insertOrIgnore，并且“共享词多次加载安全”；但 example_sentences 这张表只有自增主键，没有 (word_id, sort_order) 或 (word_id, en) 之类的唯一约束，所以重复加载时，例句行其实拦不住重复数据。这个要补唯一键，否则“多次加载安全”这句话不成立。

第二，word_id = wordText.toLowerCase().trim() 太冒险。
这个规则在你当前 ZK/GK 数据上也许能跑，但从模型上说，它默认“词面就是全局唯一 ID”。一旦以后遇到同词形不同义项、特殊词形、大小写变体、带符号词，或者未来接别的词书，碰撞概率会上来。更稳的做法是：内部主键用稳定 source key，词面只做 display；至少也要做到 book-insensitive canonical key + 可追溯原始 source key。

再说一个 推荐修正：

word_entries.cached_at 这个字段名我不建议保留。因为这轮 plan 一边强调 不改 cached_words，CET-4 路径保持不变，另一边又在新表里放一个 cached_at，会让人误以为这也是“云端缓存词表”语义。更贴切的名字应该是 imported_at 或 loaded_at，因为这批词实际上是 asset 导入，不是 runtime cache。

还有一个你这份 plan 里比较隐蔽但很重要的问题：

WordbookLoader.loadIfNeeded() 现在的判定逻辑是“只要 preset_wordbooks 里已有该 slug，就不再导入”。这意味着将来如果你更新了 zk.json 或 gk.json 内容，旧设备不会刷新。所以 preset_wordbooks 最少还要补一个 content_version、schema_version 或 content_hash，否则以后没法做词书内容升级。

再看 API 设计：

这轮不应该新增云端 REST endpoint。当前 API 基线已经明确：云端负责 today / review_group / 奖励 / 结算 / 签到，本地负责 FSRS、本地设置和部分学习运行态；而你的 plan 也把“云端 API 调用链不改”写成了硬边界。所以从 Room 1 收口看，这次是 本地内容层 + 本地 service 层扩展，不是 server API round。

但 plan 里 Step 8 改 api_client.dart 这个写法，语义上有点偏。
如果没有新增远端接口，那 WordExample 和 Word.examples 更像是 客户端域模型 / 本地内容 DTO，不该让人读起来像“API contract changed”。这一轮最好把它写成：

要么移到 study models / content models
要么明确标注：这是 app-side model extension，不是新的 cloud API contract
不然以后 Room 2 回写 API 文档时，容易产生“是不是新增了例句接口”的误解。

所以我给你的最终判断是：

可以推进，但先改 3 个点再让 Claude Code 做：

给 example_sentences 补唯一约束，保证重复加载不脏
把 word_id 改成更稳的 canonical/source key 方案
给 preset_wordbooks 补 content_version 或 hash
顺手把 cached_at 改名，并把 api_client.dart 的变更口径改成“本地模型扩展”

一句话总结：

DB 设计 80% 是对的；API 设计本质上不是“加 API”，而是“别把本地内容模型误写成云端 API 变更”。
