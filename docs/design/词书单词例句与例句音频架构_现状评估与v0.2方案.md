## Part A：现状（实测事实，不是设计稿）

### A.1 例句文本的存储与分发（现状）

```
权威源 (cloud truth)              App 实际读取的源
───────────────────                ──────────────────
PostgreSQL `examples` 表           apps/mobile/assets/words/{book-001,zk,gk}.json
  └─ 10140 行                        └─ bundle 进 APK 的 JSON
     stable_id (28 char)                每个文件 940KB / 2.25MB / 2.40MB
     word_id, en, cn, sense              合计 5.6 MB
                                     ↓ WordbookLoader.loadIfNeeded()
                                       (按 contentVersion 触发重导入)
                                     ↓
                                     drift `example_sentences` 表
                                     (设备本地 SQLite)
```

**关键事实**：
- App 学习页例句来自 **bundled JSON**，不来自 cloud API
- `/api/v1/books/:bookId/words` API 存在但 App 没用它做例句来源
- PG examples 是为了 audio_assets 外键 + 后端审计
- contentVersion 在 JSON 里硬编码（当前 '4'），bump 触发 App 全量重导

### A.2 例句音频的存储与分发（现状）

```
权威源 (cloud truth)              App 实际播放的源
───────────────────                ──────────────────
PostgreSQL `audio_assets` 表       HTTP fetch via API
  └─ 2263 行 (status='ready')         /api/v1/examples/:stable_id/audio
     id (audio_id, 28 char)            └─ 返回 { audio_id, url, ... }
     target_id = examples.stable_id    ↓
     url, checksum_sha256, ...        UrlSource(url) → audioplayers 流播
                                       ↓
mock CDN (apps/api/cdn-mock/)        本地缓存 (drift `audio_file_cache`)
  └─ NestJS useStaticAssets 挂 /cdn   └─ {appDocs}/audio/{audio_id}.mp3
     /audio/v1/examples/{locale}/        + drift row tracking LRU
     {voice}/{audio_version}/
     {shard:2}/{audio_id}.mp3
```

**关键事实**：
- 音频走 cloud-fetch → 缓存 → 本地播放，**不 bundle 进 APK**
- audio_id = `sha256_24(canonical_json([target_kind, target_id, locale, voice, format, audio_version]))`
- App 不算 hash，不拼 URL（DB §3.4 §6.2.2 强制）
- 当前覆盖率：**2263 / 10140 = 22.3%**（其余例句无音频，UI 自动隐藏喇叭按钮）

### A.3 当前发布管线（4 个脚本）

| 脚本 | 输入 | 输出 | 何时用 |
|---|---|---|---|
| `partial_publish.py --kind=example` | WAV 文件夹 | cdn-mock + audio_assets.jsonl + examples.json | Codex 出 WAV |
| `partial_publish.py --kind=word` | WAV 文件夹 | cdn-mock + audio_assets.jsonl | P2.2.B |
| `ingest_external_mp3s.py` | 已组织好的 MP3 文件夹 | cdn-mock + audio_assets.jsonl | Codex 直接出 MP3 |
| `ingest-audio-assets.ts` | examples.json + audio_assets.jsonl | PG examples + audio_assets + content_manifest | 上面任一之后 |

**典型一次例句新增的完整步骤**（8 步）：
1. LLM 改/加 wordbook source data
2. `npx ts-node scripts/export-wordbook-json.ts` → 重导出 JSON
3. **手动 bump `contentVersion`** 到下一个数字
4. Codex pipeline 跑 TTS → WAV
5. `partial_publish.py --kind=example` → cdn-mock + jsonl
6. `ingest-audio-assets.ts` → 写 PG
7. 重新 build APK + 发布给用户（**因为 bundled JSON 改了**）
8. 用户更新 App → WordbookLoader 看到新 contentVersion → 全量重导例句

### A.4 已暴露的具体问题（带数字）

#### 问题 1：例句更新需要发新 APK，节奏与音频不对称

| 资产 | 改一处的"用户拿到"路径 | 时间成本 |
|---|---|---|
| 例句**音频** | ingest 一行命令 → 用户重启即新 | 分钟级 |
| 例句**文本** | bundled JSON 改 → bump version → 重 build APK → 应用商店审核 → 用户更新 | 数天 |

**实际后果**（即使现在没用户）：
- 想紧急修一句翻译错 → 必须发 APK
- A/B 不同例句 → 不可能
- 按用户难度推不同例句 → 不可能
- 三本词书 JSON 已 5.6 MB（整 APK 一大块）

#### 问题 2：4 个脚本，文档分散，新人/自己 3 个月后回来必迷糊

#### 问题 3：Stale 资产堆积（已观测）

刚做了一次 ingest：用户 host 上 `D:/code/AI/startUp/meow/mp3/` 里有 **9221 个 mp3，只有 2289 个能匹配当前 wordbook**，剩下 **6932 个 stale 文件**（Codex 之前几版 wordbook 内容生成的，stable_id 已变）。当前 ingest 脚本不主动 GC。

云上正式 CDN 后这是真金白银。

#### 问题 4：例句和音频"完整度"不一致

App 看到的例句 100%（bundled），对应有 ready 音频的 22.3% → 大量例句没喇叭按钮。

#### 问题 5：DB v0.3.0 §1.5 设计了 manifest 但没接

v0.3.0 §1.5 原话："静态内容 = 内容包 + manifest，不是裸 CDN 文件"。当前实现：
- 音频元数据（audio_assets）→ 走了 manifest ✅
- 字典（forms / relations / phrases / morphemes）→ 进 enrichment_v2.db bundled ❌
- **例句包**→ 进 wordbook JSON bundled ❌

设计稿没替换，只是实现 lag。后续每加一条例句、每改一次翻译都在加深这个 lag。

## Part B：v0.2 长期方案

### B.1 一句话结论

> **单词全局唯一管理（words），词书是集合（books），关系靠 membership 表（word_book_memberships）；例句独立成表（examples，stable_id 内容寻址）；例句文本走 content package 分发（CDN + manifest），例句音频走 audio_assets + CDN + 本地缓存。**

### B.2 设计目标

1. 单词全局唯一管理 ✅ 已实现
2. 一本词书包含多个单词 ✅ 已实现
3. 同一个单词属于多本词书 ✅ 已实现
4. 一个单词拥有多条例句 ✅ 已实现
5. 例句发音远端拉取与本地缓存 ✅ 已实现
6. **例句文本不发版即可更新** 🟡 **本方案核心**
7. 内容包版本、校验、回滚、失败重试 🟡 **本方案核心**
8. 不改变 FSRS、奖励、结算、今日目标、Session valid 等主机制事实 owner

### B.3 当前不做（Out of Scope）

1. 不做学习页每个单词实时请求例句 API（耗带宽 + 弱网体验差）
2. 不做 per-user example recommendation
3. 不做 A/B 例句实验
4. 不做义项级 FSRS
5. 不做用户状态全面云端同步（属 P3）
6. 不做完整内容运营后台
7. 不让例句或音频失败写成学习失败
8. **不加 `example_book_memberships` 表**（v0.1 v0.2 修订点 #5）—— 当前没"按词书分例句"的产品需求；未来真有再加，结构兼容

### B.4 核心表结构设计（v0.2）

#### B.4.1 `words` —— 全局单词表 ✅ 已实现

```txt
words
- id                VARCHAR(64) PK     -- canonical lowercase, normalize_word
- word_text          VARCHAR(200) NOT NULL
- phonetic_us        VARCHAR(64)
- phonetic_uk        VARCHAR(64)
- pos_summary        VARCHAR(64)
- frequency_rank     INT DEFAULT 0
- created_at         TIMESTAMPTZ
- updated_at         TIMESTAMPTZ
```

`normalize_word` 算法**沿用 v0.3.0 r6 §3.2.1**（NFC + trim + lowercase + collapse whitespace；保留连字符/撇号/重音）。三端 reference impl 在 `apps/api/src/lib/stable-id.ts` / `apps/mobile/lib/core/util/stable_id.dart` / `apps/api/scripts/audio_pipeline/reference.py`，42 fixtures byte-identical 通过。**不重新定义。**

#### B.4.2 `books` —— 词书表 ✅ 已实现

```txt
books / word_books
- id                VARCHAR(32) PK
- display_name      VARCHAR(100) NOT NULL
- description       TEXT
- total_words       INT DEFAULT 0
- content_version   VARCHAR(32)        -- denormalized 快速指针
- sort_order        INT DEFAULT 0
- is_active         BOOLEAN DEFAULT TRUE
```

`books.content_version` 是 denormalized 快速指针；具体下载与校验由 `content_manifest` 控制（DB v0.3.0 §4.7.1 已锁定）。

#### B.4.3 `word_book_memberships` —— 词↔书 M:N ✅ 已实现

```txt
word_book_memberships
- word_id           VARCHAR(64) FK -> words.id
- book_id           VARCHAR(32) FK -> books.id
- sort_order        INT DEFAULT 0
- source_key        VARCHAR(64)
PRIMARY KEY (word_id, book_id)
```

#### B.4.4 `examples` —— 例句表 ✅ 已实现（部分）

```txt
examples
- stable_id          VARCHAR(28) PK / UNIQUE   -- v0.2 修订：与现状对齐 (28 not 32)
- word_id            VARCHAR(64) FK -> words.id
- sense_id           VARCHAR(80) NULL
- sense_label        TEXT NULL
- en                 TEXT NOT NULL
- cn                 TEXT NOT NULL
- difficulty         VARCHAR(32) NULL
- generator          VARCHAR(64) NULL
- status             active / deprecated / deleted    -- v0.2 新增（migration TBD）
- content_hash       VARCHAR(64)                       -- v0.2 新增（migration TBD）
- created_at
- updated_at
```

stable_id 算法（v0.3.0 §3.1）：
```
stable_id = sha256_24(canonical_json([word_id, normalize_text(en)]))
```

**Strategy A（v0.2 修订点 #8 锁定）**：

> stable_id 主要绑定**英文句子内容**和**音频指纹**。改中文翻译时 stable_id **不变**，只 UPDATE `cn` 字段，避免无谓让用户的收藏 + 音频缓存全部失效。改英文句子时新生成 stable_id（旧的 status='deprecated'，给客户端缓存留过渡期）。

> **此决策应进 v0.3.0 主文档 §3.5 锁死**，避免后续再讨论。

#### B.4.5 ~~`example_book_memberships`~~ —— **v0.2 删除**

v0.1 §3.5 论证："abandon 在不同词书可能用不同难度例句"。v0.2 评估：**当前没产品需求，未来未必有，YAGNI**。

加这张 M:N 表的代价：
- 所有例句读路径多一层 JOIN
- 运营生产例句要决定每条挂哪本书
- migration / API / 测试要带

收益：未来理论灵活性。**当前用 `examples.word_id` 单挂模型已够。** 真有需求时再加，结构兼容（`examples` 不变，加新表 + 改读查询）。

#### B.4.6 `audio_assets` —— 音频资源表 ✅ 已实现

```txt
audio_assets
- id                 VARCHAR(28) PK            -- v0.2 修订：与现状对齐 (28 not 32)
- target_kind        word / example
- target_id          word_id 或 examples.stable_id
- locale             en-US / en-GB
- voice              af_bella / ...
- format             mp3 / opus / aac
- audio_version      VARCHAR(32)
- url                TEXT
- checksum_sha256    VARCHAR(64)
- source_text_hash   VARCHAR(16)               -- release gate 强校验字段
- bytes              INT
- duration_ms        INT
- status             ready / pending / qc_failed / superseded
- tts_provider       VARCHAR(32)
- tts_model          VARCHAR(64)
- generated_at       TIMESTAMPTZ
```

App 不算 audio_id、不拼 CDN URL（DB §3.4 §6.2.2 强制）。

#### B.4.7 `content_manifest` —— 内容包清单 ✅ 已实现（用法待扩）

```txt
content_manifest
- id                  VARCHAR(64) PK    -- {package_name}@{content_version}
- package_name        VARCHAR(64)        -- 'audio-meta-cet4' / 'examples-zk' / ...
- package_kind        VARCHAR(16)        -- 'audio_meta' / 'examples' / 'wordbook' / 'enrichment'
- content_version     VARCHAR(16)
- file_url            TEXT
- checksum_sha256     VARCHAR(64)
- size_bytes          BIGINT
- min_app_version     VARCHAR(16)
- is_active           BOOLEAN DEFAULT FALSE
- generated_at        TIMESTAMPTZ
```

v0.2 推荐添加状态字段：`status active / deprecated / revoked`、`activated_at`、`expires_at`、`supersedes_id`（用于 grace window + 回滚）。

#### B.4.8 `content_package_state` —— 本地内容包状态表 ❌ 新增

```txt
content_package_state    (drift, device-local)
- package_id           TEXT PK   -- 对应 content_manifest.id
- package_kind         TEXT
- book_id              TEXT NULL
- content_version      TEXT
- checksum_sha256      TEXT
- local_path           TEXT
- status               pending / downloaded / verified / imported / failed
- imported_at          INTEGER UTC ms
- last_checked_at      INTEGER
- last_error           TEXT
```

**为什么单独立表，不复用 sync_state**：每个包要单独追踪 `pending / downloaded / verified / imported / failed / last_error`，sync_state 当前 schema 装不下；而且包的失败重试需要独立游标。

替代当前的"靠 `preset_wordbooks.content_version` 字符串字段判断已导入哪个版本"模式 —— 失败状态不可见、无 last_error、无重试游标。

#### B.4.9 `audio_file_cache` —— 本地音频缓存表 ✅ 已实现

```txt
audio_file_cache    (drift, device-local)
- audio_id              TEXT PK
- local_path            TEXT
- bytes                 INT
- cached_at             INTEGER
- last_played_at        INTEGER NULL
- cached_checksum       TEXT
- cached_content_version TEXT NULL
```

LRU + content_version 双触发器（DB §7.4.1）。

### B.5 App 运行时读取策略

#### B.5.1 学习页读取例句

学习页**不直接请求网络获取例句文本**。流程：

```
LearningPage
→ current word_id + active book_id
→ local SQLite 查询 examples
→ 有例句则展示
→ 无例句则隐藏例句模块（不报错）
```

#### B.5.2 例句包缺失时

如果 examples package 下载失败：
1. 学习流程不阻断
2. 例句模块隐藏（不显示大错误弹窗）
3. **使用 bundled fallback（保留至 v0.2 上线后 30 天）**
4. 不影响 FSRS、奖励、结算、今日目标

#### B.5.3 例句音频播放（已实现）

```
用户点击例句喇叭
→ App 查本地 audio_file_cache
→ 命中且 checksum 合法：DeviceFileSource 播放
→ 未命中：GET /api/v1/examples/:stable_id/audio
→ 返回 audio_id/url/checksum
→ UrlSource 流播 + 后台下载
→ 写 audio_file_cache
```

失败时：灰按钮 + 静默上报埋点；不阻断学习，不影响 rating / FSRS / 奖励。

替代当前分散的 4 个脚本。

#### B.7.2 推荐子命令

```
build-examples-package    # 从 PG examples 生成 examples-{book}.jsonl.gz
publish-example-audio     # WAV/MP3 → cdn-mock + audio_assets.jsonl
publish-word-audio        # P2.2.B 用
ingest-audio-assets       # jsonl → PG
publish-manifest          # 把新包注册到 content_manifest 并 activate
gc-stale                  # cdn-mock 里清孤儿 mp3
validate                  # release gate 校验 (source_text_hash 双阶段)
```

#### B.7.3 管线原则

1. LLM 生成例句和 TTS 生成音频**不强行做成单笔大事务**（现实部署：LLM 在云、TTS 在本地，强绑死失灵活性）
2. 但发布顺序固定："包生成 → manifest publish → stale GC"
3. 每个步骤支持 `--dry-run`
4. 每个包必须有 checksum
5. **stale GC 默认 dry-run**；真删除必须显式 `--gc`
6. 默认保留 grace window 30 天，避免旧客户端请求旧资源失败

### B.8 Stale 资产清理规则

#### B.8.1 触发条件

```
audio_id 不在当前 active audio_assets 中
AND 不在 deprecated grace window 中
AND 文件最后访问时间 > grace_days
→ 可删
```

#### B.8.2 默认策略

```bash
gc-stale --dry-run                  \ 默认仅打印计划
gc-stale --gc --grace-days 30       \ 真删
```

#### B.8.3 不允许

1. 按"当前表里没有"立刻硬删
2. 无 dry-run 模式
3. 不记录删除报告
4. 删除 still-active / deprecated grace window 内资源

### B.9 数据变更场景

#### B.9.1 新增一个单词

```
1. INSERT words
2. INSERT word_book_memberships if 入某本书
3. INSERT examples (with stable_id)
4. (Optional) generate audio + INSERT audio_assets
5. publish-manifest
```

#### B.9.2 某本词书新增已有单词

```
INSERT word_book_memberships(word_id='abandon', book_id='ielts', sort_order=...)
```
不复制 words。

#### B.9.3 某本词书删除一个单词

```
UPDATE word_book_memberships SET status = 'deprecated'
WHERE word_id = 'abandon' AND book_id = 'ielts'
```
不删 words。

#### B.9.4 修改某条例句**英文文本**

```
1. 旧 examples.status = 'deprecated'
2. 生成新的 stable_id (因 normalize_text(en) 变了)
3. INSERT 新 examples
4. 旧 audio_assets 进 deprecated grace window (status='superseded')
5. 新例句触发新音频生成
6. publish-manifest 推 examples package + audio meta 新版本
```

#### B.9.5 修改某条例句**中文翻译** —— **Strategy A（v0.2 锁定）**

```
UPDATE examples SET cn = ?, content_hash = ?, updated_at = NOW()
WHERE stable_id = ?
```
**stable_id 不变** —— 因为 stable_id 绑英文句子和音频，翻译微调不该让收藏 + 音频缓存失效。

### C.1 反方观点（v0.2 作者主动列）

为防 echo chamber，v0.2 列出**反对自己方案的可能论据**，请评审认真考虑：

**反对 Phase 1+2 合并 / 例句 CDN 化**：

1. **首启体验代价**：例句搬 CDN 后用户首次启动 / 进新词书需拉网。弱网 / 离线场景体验恶化（v0.2 用 bundled fallback 缓解，但 fallback 删除后无解）
2. **MVP 阶段过早优化**：还没用户，APK 里 bundled 5.6MB 没人喊。等用户量到一定规模再搬不晚
3. **CDN 费用**：mock 阶段不要钱，真实 CDN 后例句包请求次数 = 用户数 × 词书数
4. **复杂度上升**：要加 manifest 拉取 + 包下载 + 校验 + 解包 + 导入 + 失败回退 + 增量更新一整套
5. **审核风险**：用户首启拉的例句包里若有审核敏感词（恋爱 / 宗教 / 政治），App Store 审核风险

7. **6932 stale 不算紧急**：本地 host 上的事，没用户感知，等真需要时再加 GC

**反对 v0.2 删除 example_book_memberships**：

8. **未来改回成本高**：现在多设计一张 M:N 表代价小；以后真要"按词书分例句"再 migration 头大
