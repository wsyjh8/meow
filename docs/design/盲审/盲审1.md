基于上传文档实读做软件工程设计评审，不按既有结论“缓存式附和”。文档现状里明确：例句文本来自 bundled JSON，不来自 API；例句音频走远端定位与本地缓存；当前例句音频覆盖率 22.3%，且例句 JSON 约 5.6MB、stale MP3 约 6932 个。

## 总判断

v0.2 的方向对，但**下一周不建议直接做完整“例句 CDN 化”**。它把内容包、manifest、客户端下载、校验、解包、导入、fallback、回滚、GC 都打包成一个大切面；对 solo MVP 来说，风险不是“能不能实现”，而是**出问题时不好定位、难回滚、测试矩阵暴涨**。

我的推荐是：**先做 Phase 0.5，但把它升级成“内容发布可靠性最小闭环”**，而不是单纯合脚本。

## Q1：A.4 里哪个判断有问题？漏了什么？

判断基本成立，但**问题 4“例句和音频完整度不一致”不应被归类为架构问题**。22.3% 音频覆盖率更像内容生产进度 / 产品体验问题；只要 UI 能隐藏按钮、不阻断学习，它不是系统设计缺陷。文档也已经说明失败不应影响 FSRS、奖励、结算等主流程。

漏掉的更严重问题是：**发布一致性与回滚语义没被完全建模**。例如：

1. `word_book_memberships` schema 没有 `status`，但 B.9.3 却写了 `UPDATE word_book_memberships SET status = 'deprecated'`，这是设计内不一致。
2. `content_manifest active=true` 的激活需要原子性：同一个 `package_name + book_id` 同时只能有一个 active，否则客户端拿包会不确定。
3. 中文翻译改动 stable_id 不变是对的，但必须明确 `content_hash`、`package_version`、本地导入幂等之间的关系，否则“同 stable_id 内容变化”会让客户端去重、收藏、复习引用、音频缓存出现隐性歧义。

## Q2：是否删除 `example_book_memberships`？

选 **C：折中**。

不立即建表是对的，当前没有产品需求，不该为了理论灵活性给所有读路径加 JOIN。但不应只写“未来再加”。建议现在在设计文档中冻结一个**未来兼容扩展点**：

```txt
example_book_memberships(
  example_stable_id,
  book_id,
  sort_order,
  difficulty_override,
  status
)
```

现在不迁移、不实现、不接读路径；只保证 `examples` 表和 package 格式未来能兼容“按词书筛例句”。这样避免过早实现，也避免未来拍脑袋迁移。

## Q3：Phase 1 + Phase 2 合并是否合理？

选 **C：Phase 1 应重新定义**。

“memberships 已完成，所以合并”这个理由不够好。真正的 Phase 1 不该是 membership，而应是：

> **Content Release Contract v1：包格式、manifest 激活规则、校验、回滚、dry-run、幂等导入语义。**

然后 Phase 2 再做 mobile manifest-driven 下载导入。否则一个 PR 同时动 PG migration、pipeline、API、Drift schema、WordbookLoader、fallback、测试，单 PR 爆炸。

## Q4：下一周单选推荐

选 **A：Phase 0.5 管线收口**。

理由：它成本最低、风险最低、能立刻减少发布混乱，并且是 Phase 1+2 的前置安全网；没有统一 pipeline、dry-run、validate、GC 报告，直接做 CDN 化会把现有混乱扩大到客户端分发层。

## Q5：长期根本性误区

最大误区是：**把“静态内容分发”当成文件下载问题，而不是内容供应链问题**。

长期要补的是 release engineering，而不是更多表：

```txt
source data
→ deterministic build
→ validation gate
→ artifact registry
→ manifest activation
→ client import
→ telemetry
→ rollback
→ GC
```

现在文档已经有 manifest、checksum、grace window 的雏形，但还缺“发布不可变 artifact + 可回滚 active 指针 + 客户端导入遥测”。这比是否 CDN 化例句更根本。
