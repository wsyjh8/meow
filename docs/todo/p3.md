## 1. 你这轮要做什么

你现在要做的，是把 **本地 snapshot** 通过一条最小上传链路送到 **cloud backup container**，并把 **最近一次备份状态** 和 **设置页 / 我的页里的最小入口** 一起打通。

一句话：

> **把“能导出”推进到“能手动备份到云端并让用户看懂最近一次备份结果”，但仍然不把产品做成云同步系统。**

### 本轮允许做
1. 建立 snapshot upload API 调用链路
2. 建立最小 cloud backup container 对接层
3. 落 latest backup status 的读取 / 映射 / 展示
4. 在设置页 / 我的页增加最小入口
5. 落 upload 中 / 成功 / 失败 / retry 的状态矩阵
6. 建立与 upload 对应的测试和回归

### 本轮禁止做
1. 不做 restore
2. 不做 delete cloud backup 主入口
3. 不做 clear local data 主入口
4. 不做 full sync / auto sync / background sync
5. 不做多设备冲突解决
6. 不把 upload success 写成 sync success
7. 不把“有云端备份”写成“当前设备已恢复”
8. 不把入口放到 Today 主链路中心
9. 不新增完整 backup center 大页面（若没有上游单独 pin）

## 2. 你必须服从的事实边界

### 2.1 当前 P3.1 产品立场
P3.1 的正式名称是：

> **Local Progress + Cloud Backup**

当前冻结立场是：

- **local-first**
- **manual backup**
- **backup-first**
- **不是 real-time sync**
- **不是 multi-device merge**
- **restore 继续 gated**

### 2.2 三类成功语义必须严格分开
你必须继续严格分开：

1. **local export success**
2. **cloud upload success**
3. **restore success**

本轮只新增并实现第 2 类。

必须写硬：

- `local export success != upload success`
- `upload success != sync success`
- `has latest cloud backup != restore completed`
- `upload failed` 不能被弱化成“稍后会自动同步好”

### 2.3 cloud backup container 的准确角色
云端当前只是：

> **backup container**

不是：
- runtime truth
- sync truth
- merge engine
- recovery platform
- cross-device live state

### 2.4 UI / UX 边界
入口应该在：
- 设置页
- 我的页
- 轻支持位置

不应该：
- 插到 Today 核心任务卡中心
- 干扰学习页 / 复习页 / Session
- 用“云同步”“自动同步”“所有设备已一致”这类表达误导用户

### 2.5 高风险动作默认继续不开放
未单独 pin 前，以下动作默认不做成可执行主流程：
- restore
- delete cloud backup
- clear local data

如果为占位需要出现：
- 只能隐藏 / disabled / pending
- 不能出现可执行成功流

## 3. 这轮应该实现什么

## 3.1 Upload adapter / service
请建立最小上传链路，名称按项目风格即可，例如：
- `BackupUploadService`
- `CloudBackupRepository`
- `UploadSnapshotUseCase`

它至少要做：
1. 接收 Phase 2 已冻结的 snapshot payload
2. 调用后端最小 upload API
3. 处理成功 / 失败 / retryable / non-retryable
4. 返回明确的 upload result 对象

### 3.1A Upload result 对象
建议至少包含：
- `status`
- `backupId`（若服务端返回）
- `uploadedAt`
- `errorCode`
- `retryable`
- 可选：`serverRecordedSchemaVersion`

注意：
- 这是 upload result
- 不是 sync result
- 不要长出 `syncHealthy` 之类会误导的命名

## 3.2 Latest backup status
你需要建立并展示“最近一次备份状态”。

这轮默认规则要写死：

> **默认展示的是最近一次上传结果，不是最近一次本地导出结果。**

如果既有 export success 又有 upload result，展示优先级：
1. 最近一次上传状态
2. 若只有本地导出成功、但未上传，则只能作为次级说明
3. 不能把“本地已导出”写成“云端已备份”

### 最小状态集合
至少要支持：
- `no_backup_yet`
- `upload_in_progress`
- `upload_succeeded`
- `upload_failed`
- `retrying`
- 可选：`temporarily_unavailable`

## 3.3 Minimal user entry
请在 **设置页 / 我的页** 增加最小入口与最小状态展示。

### 最小入口应包含
1. `立即备份`
2. `最近一次备份状态`
3. 最近一次备份时间（若有）
4. 失败时的 `重试`

### 本轮默认不包含
1. restore 主按钮
2. delete backup 主按钮
3. clear local 主按钮
4. 多设备说明页
5. 完整 backup center 大页面

## 3.4 最小状态矩阵
你必须把状态矩阵做清楚，至少包含：

### A. no_backup_yet
- 展示中性说明
- 可以有“立即备份”

### B. upload_in_progress
- 主按钮进入 loading / disabled
- 显示中性文案，如“正在备份中”
- 不能写成“正在同步全部设备”

### C. upload_succeeded
- 显示最近一次上传成功时间
- 可以展示“已备份”
- **不能**写成“已同步”

### D. upload_failed
- 显示失败状态
- 允许展示“重试”
- 不要责备用户

### E. retrying
- 与 upload_in_progress 类似，但可有“正在重试”
- 仍不能写成“同步修复中”

### F. temporarily_unavailable
- 若服务暂不可用，给中性系统态提示
- 不写成用户操作错误

## 4. 文案与状态表达硬边界

### 4.1 允许的表达
- 已备份
- 备份中
- 备份失败
- 可重试
- 最近一次备份
- 最近一次上传成功
- 尚未备份

### 4.2 禁止的表达
- 已同步
- 所有设备已同步
- 云端已成为最新真相
- 已恢复
- 已自动同步完成
- 数据已全平台一致

### 4.3 一个必须写硬的原则
> **`displayed latest backup status` 不是 `fresh sync truth`。**

用户能看到最近一次备份状态，不等于系统已经具备完整同步能力。
