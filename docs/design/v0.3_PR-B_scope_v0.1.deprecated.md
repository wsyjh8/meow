## 1. PR-B1 —— 发布侧补全（server only，5-7 天）

### 1.1 范围

### 1.2 三个交付物

#### 1.2.1 `orphan-scan` 子命令

**目的**：扫物理文件，找出 PG 没指向的 FS 孤儿（FS 残留）。

**两类扫描根目录**（探索后修正——v0.3 PR-B 评审采纳 P1）：

| 类别 | FS 根目录 | 对应 PG 表 / 字段 |
|---|---|---|
| audio orphan | `apps/api/cdn-mock/` | `audio_assets.url` |
| package orphan | `apps/api/audio-pipeline-staging/` | `content_manifest.file_url` |

`audio_assets.url` 真实数据形如 `local://cdn/audio/v1/...` 或 `file:///D:/.../cdn-mock/...`。
`content_manifest.file_url` 真实数据形如 `file:///D:/.../audio-pipeline-staging/...@vN.jsonl.gz`。
两个完全不同的目录树，必须分开扫。

**典型场景**：
- 发布管线异常中断（写文件成功但 PG 记录失败）
- 手工删 PG 行（DBA 误操作）
- 历史脚本（pre-PR-A）留下的不一致

**接口**（draft）：
```bash
python pipeline.py orphan-scan [--dry-run|--clean] \
  [--cdn-mock-dir cdn-mock] [--staging-dir audio-pipeline-staging] \
  [--scope {audio|packages|all}]
```

- 默认 `--dry-run`，列候选 + 各自尺寸 / mtime
- `--clean` 显式删除（与 dry-run 互斥）
- `--scope` 默认 `all`，可限定单边
- 防误删：白名单（仅 root 子树内、仅 .mp3/.gz/.br/.jsonl 后缀、拒绝 symlink / 隐藏文件）

**与 gc-stale 区别**：
- `gc-stale` 是 PG 状态机驱动（PG 有行 + status='eligible_for_gc' → 删 FS）
- `orphan-scan` 是 FS 驱动（FS 有文件 + PG 无对应行 → 删 FS）

#### 1.2.2 `rollback` 子命令

**目的**：把已被替换下线的旧 release 重新 reactivate，撤回最新 release。

**典型场景**：
- 新版本上线后发现严重 bug，需要快速回到上一版
- A/B 灰度结果不满意，回滚到对照组

**接口**（v0.2 评审采纳 R1#3 / R2#4：CLI 形态统一 positional，与 validate/activate/revoke/deprecate 一致）：
```bash
python pipeline.py rollback <release_id> --reason TXT [--yes]
```

**语义**（v0.3 PR-B 评审采纳 P2 收紧）：
1. target release 必须是 **`deprecated` 状态**——不允许从 `revoked` 恢复
2. 找当前 active release（如有）→ 转 `deprecated`（cascade is_active=false；reason=rollback）
3. target → `active`（cascade is_active=true）
4. 写双方 activation_log

**关键约束**：
- **只允许 `deprecated → active`**，不允许 `revoked → active`（revoke 是硬撤回，由
  scope doc 术语表规定不可逆——若放开则与之冲突）
- 如果 target 的 manifest 文件已被 gc-stale 删（FS 不存在）→ 拒绝 rollback（防止
  "状态机活了但用户拿不到包"）
- 必须 stdin 确认 + `--yes` 跳过

**与 revoke / deprecate 的关系（明确边界）**：

| 命令 | 转换 | 是否可恢复 |
|---|---|---|
| `deprecate` | active → deprecated | ✅ 可被 rollback 重新激活（软下线） |
| `revoke` | active/deprecated → revoked | ❌ 永不恢复（硬撤回） |
| `rollback --to <id>` | deprecated → active（同时把当前 active → deprecated） | —— |

**v0.3 §B.4.5 状态机扩展**（仅一条新转换）：
```
[deprecated] ── rollback ──▶ [active]   (PR-B1 加，需校验 manifest 文件存在)
```

**revoked 永远不能再 active**——若需"硬撤回后又想恢复"，唯一路径是
`create-release` 起新 release（新 ID）走完整 publish + validate + activate 流程。

#### 1.2.3 审批工作流 CLI

**目的**：让 release 在 `validated → active` 之间多一个 `approved_by` 必填关卡，治理审计完整。

**典型场景**：
- 双人审核：发布者跑 validate，运营跑 approve，开发者跑 activate
- 监管合规：每次发布必须有审批人记录

**接口**（draft）：
```bash
python pipeline.py approve <release_id> --approver <user_id> [--note TXT]
```

**语义**：
1. release 必须是 `validated` 状态
2. UPDATE `content_release.approved_by = $1`
3. activate 子命令前置校验：如果 `content_release.approved_by IS NULL` 则拒绝 activate

**配置**：
- 通过环境变量 `CONTENT_RELEASE_REQUIRE_APPROVAL=true` 开关（默认 false 兼容 PR-A 行为）
- 如果 false：approved_by 字段仍可写入（审计），但 activate 不强制

**审批人模型**（PR-B1 简化）：
- `--approver` 接 string，自由 ID（如 `wsyjh8` / `editor-001`）
- 不连用户表（PR-A 没有用户系统，强行连风险高）
- PR-B3 加 Web UI 时再做角色 / 双签

### 1.3 需要的 schema 改动

零 schema 改动 —— PR-A migration 007 已留 `content_release.approved_by VARCHAR(64)` 字段。
仅需用 application logic 兜住语义。

### 1.4 e2e 覆盖

- `orphan-scan --dry-run` 检测出 audio + package 两类孤儿
- `orphan-scan --clean` 真删 + PG 反查无影响（两个目录都验）
- `orphan-scan --scope audio` / `--scope packages` 单边隔离
- `rollback` 完整链：active(v2) + deprecated(v1) → rollback v1 → v2 deprecated, v1 active → API 反查回 v1
- `rollback` 拒绝路径：rollback 到 draft / validated / **revoked**（评审采纳 P2）/ FS 文件丢失
- `approve` + `activate` gating：未 approve 时 activate 拒绝 / approve 后通过
- `CONTENT_RELEASE_REQUIRE_APPROVAL=false` 时 activate 不卡

期望 e2e 数：34 (PR-A) + ~10 = ~44。

### 1.5 不做（明示延后）

- 审批 Web UI（PR-B3）
- 双签（multi-approver）（PR-B3）
- rollback 到任意版本图（多级 history navigator）（PR-C 候选）
- orphan-scan 自动安排（cron）（运维侧，独立）

### 1.6 风险

| 风险 | 缓解 |
|---|---|
| rollback 状态机扩展破坏 PR-A 既有 VALID_TRANSITIONS | 加新转换前严格 e2e；保留所有现有路径不变 |
| orphan-scan 误删非 cdn-mock 内的文件 | 严格 path 白名单；dry-run 默认；--clean 显式确认 |
| 审批开关默认 false 导致后续忘开 | README + commit message 写明；监控告警放 PR-C |

## 2. PR-B2 —— App 端 manifest 消费（mobile only，5-8 天）

### 2.1 范围

让 Flutter App 真正消费 PR-A 的 `GET /api/v1/content/manifest`，把包下载、校验、
落地、缓存失效完整跑通。**不动 server**（cdn-mock 路径 + dual-condition 已就绪），
**不接真 CDN**（继续打 `http://localhost:3000/cdn/` 或 dev 机 LAN）。

### 2.2 五个交付物

#### 2.2.1 ManifestClient

- `GET /api/v1/content/manifest?since_release=...&app_version=...`
- 返回 `{release_ids, packages[]}` 反序列化到 Dart class
- 失败重试（指数退避，3 次）+ network down 优雅降级

#### 2.2.2 DownloadManager

- 给定 `package` → 下载 file_url 到 cache dir
- 流式下载 + 进度回调（UI 进度条）
- sha256_24 验证（与 manifest.checksum_sha256 比对）
- 失败 retry / 部分下载续传（HTTP Range）
- 多包并发下载控制（max 2 并行，避免抢带宽）

#### 2.2.3 PackageInstaller

- 解压 `.gz` → 落地到 drift / files dir
- 按 `package_kind` 分发：
  - `examples` → 写入 drift `example_sentences` 表
  - `audio_meta` → 写入 drift `audio_file_meta` 表
  - `wordbook` → 写入 drift `word_books` 表
  - `dictionary` → 写入 drift `dictionary` 表
- 原子替换：临时表 swap 或 transaction wrap

#### 2.2.4 CacheInvalidator

- 监听新 release 的 `release_ids`
- 对比本地状态：哪些 package 是新的、哪些是更新、哪些被 deprecate
- 触发 PackageInstaller 重装新 / 更新的
- deprecate 的不主动清，留 grace 期（避免用户网络差时本地老包还能用）

#### 2.2.5 启动联动

- App 冷启动时（或定期）调 ManifestClient
- 后台静默更新（不阻塞 UI）
- 首次安装：拉全量
- 已有状态：传 last release_id 拉增量

### 2.3 schema 改动

drift 端可能需要：
- `local_content_state` 表（记录本地各 package 的 release_id / 安装时间 / 版本）
- 详细字段在 PR-B2 plan 里定

server 端：**零改动**（PR-A 已就绪）。

### 2.4 e2e 覆盖

- 集成测试：mock manifest API → DownloadManager → PackageInstaller 全链条
- 失败注入：网络中断 / checksum mismatch / 解压失败
- 增量场景：first install / update / deprecate
- 字段单测：CacheInvalidator 状态比对逻辑

### 2.5 不做（明示延后）

- 真 CDN（PR-B3）
- 离线模式（assume always online for fetch；缓存命中走 offline）—— 但本地缓存命中仍然 offline 可用
- 后台进程 / 通知中心集成（iOS / Android 的 BackgroundFetch）（PR-C 候选）
- A/B 灰度 client-side（按设备 ID 路由不同 release）（PR-C 候选）

### 2.6 风险

| 风险 | 缓解 |
|---|---|
| drift schema migration 破坏现有用户数据 | 用 drift migration 标准流程；本地 backup + 测试 upgrade 路径 |
| 大包下载阻塞 UI | DownloadManager 全部走 isolate / background |
| 多包并发下载抢带宽 | max 2 并行 + 优先级队列 |
| checksum mismatch 反复 retry 死循环 | retry 上限 3 次后告警 + 标记 package 为 broken |

## 附录 A：术语对照表

| 术语 | 定义 |
|---|---|
| release | content_release 行，治理 SSOT |
| package | content_manifest 行，物理包文件元数据 |
| package_set | release.package_set 数组（denormalized snapshot） |
