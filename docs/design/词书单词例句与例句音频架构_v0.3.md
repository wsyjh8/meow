## Part B：v0.3 长期方案

### B.1 一句话结论（v0.3 升级版）

> 内容是**可发布、可校验、可回滚的 release**，不是文件。`content_release` 是治理 SSOT，`content_manifest` 是它的客户端投影。例句文本走 release-driven CDN package，例句音频走 release-driven audio_assets + CDN，App 用 minimum-set bundled 兜底永久离线场景。

### B.2 核心概念分层

```
治理层 (governance)        ← v0.3 新增
─────────────────────
content_release           「这一批要一起发布的内容」
                          - release_id
                          - package_set (examples-zk@v5, audio-meta-zk@v5, ...)
                          - status (draft → validated → active → deprecated → revoked)
                          - rollback_target_release_id
                          - generated_by / activated_at / revoked_at

  ↓（投影）

分发层 (distribution)
─────────────────────
content_manifest          客户端按 manifest 拉包，但 manifest 行只有当 release.status='active' 才存在
audio_assets              单条音频元数据，状态机管理（见 §B.4.6）
                          → CDN 文件

  ↓（消费）

设备层 (device)
─────────────────────
content_package_state     本地包状态（pending/downloaded/verified/imported/failed）
audio_file_cache          本地音频文件缓存
example_sentences (drift) 本地导入的例句行
```

**关键不变量**：
- 客户端**不直接读 release 表**（看不见治理层）
- 客户端**只看 manifest 中状态为 active 的包**
- 治理层异常（半发布 / 校验失败 / 回滚中）→ manifest 上看不到对应行 → 客户端无感降级

### B.4 核心表结构

#### B.4.1 ✅ `words` / `books` / `word_book_memberships`

沿用 P1 已实现版本。`words.id` 用 normalize_word 算法（v0.3.0 §3.2.1，不重复定义）。

#### B.4.2 ✅ `examples` —— v0.3 加锁字段

```txt
examples
- stable_id          VARCHAR(28) PK / UNIQUE
- word_id            VARCHAR(64) FK -> words.id
- sense_id           VARCHAR(80) NULL
- sense_label        TEXT NULL
- en                 TEXT NOT NULL
- cn                 TEXT NOT NULL
- difficulty         VARCHAR(32) NULL
- generator          VARCHAR(64) NULL
- status             active / deprecated / deleted    -- migration 007 加
- content_hash       VARCHAR(64)                       -- migration 007 加，语义见下
- created_at / updated_at
```

**stable_id 算法**（v0.3.0 §3.1）：
```
stable_id = sha256_24(canonical_json([word_id, normalize_text(en)]))
```
**永远不升级**（用户决策不做难度分级，无算法演进需求；盲审 7 观察 1 警报解除）。

**Strategy A 锁定**（v0.2 § B.4.4 不变）：改 cn/sense_label/difficulty 不动 stable_id；只改 en 才生成新 stable_id。

**🆕 `content_hash` 语义锁定**（盲审 7 #2）：

```
content_hash = sha256(
  en + "" +     --  作字段分隔符避免歧义
  cn + "" +
  (sense_label OR "") + "" +
  (difficulty OR "")
)
```

用途：
- 客户端按行 diff：本地 `examples` 行的 content_hash != 包内同 stable_id 的 content_hash → 用包覆盖本地行
- 不入 stable_id（stable_id 只绑英文 + word_id），但是包内每行必带

这样 cn 翻译改动可以触发客户端单行更新，不需要全包重导。**修一个翻译错误 → 包文件 size_bytes 几乎不变 → 客户端只更新这一行**。

#### B.4.3 ✅ `audio_assets` —— v0.3 加状态机

```txt
audio_assets
- id (audio_id)         VARCHAR(28) PK
- target_kind            word / example
- target_id              word_id 或 examples.stable_id
- locale / voice / format
- audio_version          VARCHAR(32)
- url
- checksum_sha256        VARCHAR(64)
- source_text_hash       VARCHAR(16)
- bytes / duration_ms
- status                 ready / superseded / qc_failed / eligible_for_gc / deleted -- v0.3 状态机
- transitioned_at        TIMESTAMPTZ                    -- v0.3 加，状态机审计
- transition_reason      TEXT NULL                       -- v0.3 加，审计/排错
- tts_provider / tts_model
- generated_at
```

**🆕 状态机**（盲审 7 #5）：

```
                    新版本 publish
   ready ─────────────────────────────► superseded
                                              │
                                              │ grace_days 过期
                                              │ 且无客户端引用
                                              ▼
                                        eligible_for_gc
                                              │
                                              │ gc-stale --gc 显式确认
                                              ▼
                                          deleted (软删,行保留作审计)
```

GC 是**状态机查询**（`SELECT * WHERE status='eligible_for_gc' AND transitioned_at < now()-30d`），不是 set diff。这样发布中间态、灰度回滚态、grace 内资源都不会被误删。

#### B.4.4 ❌ `example_book_memberships` —— **永远不建表**

用户决策 0.1.2：所有词书共享同一例句池。**v0.3 删除 v0.1/v0.2 里所有"未来兼容""按 book 取例句"的措辞**。读路径永远是：

```sql
SELECT * FROM examples WHERE word_id = $1 AND status = 'active' ORDER BY ordinal
```

不带 book_id。盖章。

#### B.4.5 🆕 `content_release` —— 治理层 SSOT

```txt
content_release    (PG)
- release_id              VARCHAR(64) PK    -- 例: 'release-2026-05-05-001'
- title                   TEXT              -- 人类可读，例: 'Fix translation typos in zk'
- package_set             JSONB             -- ['examples-zk@v5', 'audio-meta-zk@v5']
- target_min_app_version  VARCHAR(16)
- status                  draft / validated / active / deprecated / revoked
- rollback_target_id      VARCHAR(64) NULL  -- 回滚指向的旧 release
- generated_by            VARCHAR(64)        -- 'pipeline.py@user' / 'manual'
- approved_by             VARCHAR(64) NULL   -- 未来审核流程接入点
- created_at / activated_at / revoked_at
- activation_log          JSONB              -- 状态转换审计 [{from, to, at, reason}]
```

**激活契约**：
1. 一个 release 的所有 package 必须先各自 status='validated' 且 CDN 文件已上传
2. `release.status='active'` 时，**事务地** 把 package_set 里每个包写入 `content_manifest` (is_active=true)
3. 上一个 release 自动转 `deprecated`（除非显式标记 `expires_at`）
4. Revoke 时事务地从 manifest 删行 + release.status='revoked'

**回滚**：
```sql
\ rollback release-2026-05-05-001 → release-2026-05-04-003
UPDATE content_release SET status='revoked', revoked_at=NOW(), rollback_target_id='release-2026-05-04-003' WHERE release_id='release-2026-05-05-001';
\ 同事务恢复旧 release 的 manifest 行
```

#### B.4.6 ✅ `content_manifest` —— 改为 release 投影

v0.3 不再独立存在。由 release 激活时事务写入。客户端协议不变，但**手工 INSERT manifest 在 v0.3 之后视为反模式**。

```txt

- min_app_version / is_active
- generated_at
- release_id           VARCHAR(64) FK -> content_release.release_id   -- 🆕 v0.3
```

### B.5 App 运行时读取策略

#### B.5.1 学习页读取例句（不变）

```
LearningPage → drift example_sentences WHERE word_id = ? AND status = 'active'
```

#### B.5.2 启动时拉取 manifest（v0.3 新流程）

```
App 启动
  ↓
GET /api/v1/content/manifest?since_release=<local_last_release_id>&app_version=<X>
  ↓
manifest 返回新 active 包列表
  ↓
对每个包：
  - 检查 content_package_state，若已 imported 同 version 跳过
  - else: 异步下载 (file_url) → 校验 checksum → 进 content_package_state.status='verified'
  - 解包 → 按 stable_id + content_hash 做 row-level diff → upsert 到 example_sentences
  - 全部行处理完 → status='imported'
  - 任一步失败 → status='failed' + last_error，不阻断学习
```

#### B.5.3 minimum-set bundled fallback（v0.3 替代"30 天后删全包"）

```
APK 永远 bundle:
  apps/mobile/assets/words/minimum-set.json (~600KB)
  └─ 第一本词书 (book-001/CET-4) 的核心 200 词 + 各 1 例句
```

启动逻辑：
```
if 设备从未成功 imported 任何 examples package:
  使用 minimum-set 兜底
else:
  使用 imported 数据（即使 manifest 拉取失败也不退回 minimum-set）
```

收益：
- **新装永久离线用户**始终有内容可学（不会拉空）
- APK 体积从 5.6MB → 600KB（减 89%）
- CDN 失败不影响首启首屏

### B.7 内容发布管线（v0.3 升级版）

#### B.7.1 单一 entry: `apps/api/scripts/content_pipeline/pipeline.py`

子命令：

| 子命令 | 作用 | 状态机入口 |
|---|---|---|
| `build-examples-package <book>` | 从 PG examples 导 jsonl.gz + checksum | 写 release.draft |
| `publish-example-audio <release>` | WAV/MP3 → cdn-mock + audio_assets 写 ready | release.draft |
| `publish-word-audio <release>` | P2.2.B 用 | release.draft |
| `validate <release>` | release gate：所有包 checksum / source_text_hash / CDN 文件存在性 | draft → validated |
| `activate <release>` | 事务激活：写 manifest + 上版 release 转 deprecated | validated → active |
| `revoke <release>` | 紧急回滚：从 manifest 删行 + release.status='revoked' | active → revoked |
| `gc-stale [--dry-run \| --gc]` | 状态机查询 eligible_for_gc，默认 dry-run | superseded → deleted |

#### B.7.2 发布原则

1. **每步都支持 `--dry-run`**
2. `validate` 失败时**绝不进 active**（无 `--bypass` flag）
3. `activate` 是事务：manifest 写入 + release 状态变更同一 PG transaction
4. `gc-stale` 默认只打印 candidate，删需要显式 `--gc`
5. 所有状态转换写入 `content_release.activation_log`（审计追溯）

### B.8 Stale 资产清理（v0.3 状态机版）

#### 触发条件（不再是 set diff）

```sql
SELECT * FROM audio_assets
WHERE status = 'eligible_for_gc'
  AND transitioned_at < NOW() - INTERVAL '30 days'
```

进入 `eligible_for_gc` 的条件：
```
status='superseded' AND transitioned_at < NOW() - INTERVAL '30 days'
AND audio_id 不在任何 active release 的 package 引用列表
```

CDN 文件删除：
```bash
gc-stale --gc --grace-days 30
```

#### 不允许

1. set diff 式硬删（无视状态机）
2. 跳过 dry-run 直接删
3. 删 status='superseded' 仍在 grace 内的资源
4. 删 status='ready' 资源（即使 audio_id 不在当前 release）

### B.9 数据变更场景（v0.3 加 release 视角）

#### B.9.1 修改一条例句**英文文本**

```
1. 旧 examples.status = 'deprecated'
2. 计算新 stable_id（normalize_text(en) 变了）
3. INSERT 新 examples 行 (status='active', content_hash=新)
4. 旧 audio_assets 触发器：transition status='ready' → 'superseded', transitioned_at=NOW()
5. 新例句调度生成新音频（pipeline.py publish-example-audio）
6. 新 release 包含：examples-zk@v6 + audio-meta-zk@v6
7. validate → activate
```

#### B.9.2 修改一条例句**中文翻译**（Strategy A）

```
1. UPDATE examples SET cn=?, content_hash=新, updated_at=NOW() WHERE stable_id=?
   stable_id 不变，audio_assets 不动
2. 重新 build examples-zk 包（新 content_hash 在包里）
3. 新 release 包含：examples-zk@v7（不含 audio-meta）
4. 客户端拉新包，row-level diff：本地行的 content_hash != 包里的 → 覆盖 cn 字段
5. 用户音频 / 收藏 / 缓存全部不受影响
```

### B.13 5 年盲点占位（不实现，留位置）

#### B.13.1 Observability（盲审 7 #5）

**长期需要**：

**长期需要**：客户端 `If-None-Match: <etag>` 让 manifest 大部分启动返 304，CDN/server 节流量。

**v0.3 不做**：since_release 参数已经避免了大部分全量返回。真上 CDN 时再加。

#### B.13.4 `review_state` 内容审核工作流（盲审 4/5/6/7 共识）

**长期需要**：当真有内容运营 + 法务审核时，每条 examples / audio 需要 `draft → pending_review → approved → rejected` 流转，approved 才能进 `content_release.draft`。

**v0.3 不做**：当前 solo + LLM 生成 + 自审。但 `content_release.approved_by` 字段已经预留位置，未来接审核流不破坏 release schema。
