## 总体判断

v0.2 的大方向是对的：**例句文本从 APK bundle 迁到 manifest-driven content package**，符合静态内容可发布、可校验、可回滚的长期形态。但我不建议下一周直接做完整 Phase 1+2；当前更危险的是**发布链路不可控**，不是 APK 多 5.6MB。

---

## Q1：5 个问题里哪个判断错了？漏了什么更严重的问题？

**问题 4 的归因不完全对。**
“例句 100%，音频 22.3%”是内容生产完整度问题，不是分发架构问题。把例句 CDN 化不会自动提升音频覆盖率，反而可能让“文本更新快、音频追不上”的不一致更频繁。真正要管的是 release gate：某个例句包发布时，是否允许缺音频、缺到什么比例、UI 如何声明。

**漏掉的更严重问题：包与包之间缺少一致性边界。**
现在方案把 examples package、audio_assets、content_manifest、CDN 文件、客户端 SQLite import 分散处理，但没有明确定义一个“内容 release”的原子单位。例如：

* `examples-zk@v5` 已激活，但对应 audio meta 还没激活；
* manifest 指向的包下载成功，但客户端导入一半崩溃；
* 英文例句改了 stable_id，旧音频进入 grace window，但新包和新音频不是同一批次发布；
* 回滚 examples 包后，audio_assets 是否同步回滚不清楚。

这比“是否 bundle 5.6MB”更核心。长期应引入 `content_release` / `release_id` 概念，把 examples package、audio meta、enrichment package 绑定到同一个 release 批次，manifest 只是 release 的投影。

---

## Q2：是否删掉 `example_book_memberships`？

**选 C：保留 schema 设计，但不立即建表。**

现在不建表是对的，MVP 不该为了“未来可能按词书分例句”增加 JOIN、运营负担和测试面。但要在主设计里预留迁移路径：

```txt
examples.word_id 先满足当前需求
未来新增 example_book_memberships(example_id, book_id, sort_order, difficulty_override, status)
```

关键是不要把当前代码写死成“一个 word 的所有例句对所有 book 永远等价”。查询层可以先封装成 `getExamplesForWord(bookId, wordId)`，内部现在只查 `examples.word_id`，未来再切 JOIN。这样既 YAGNI，又不把未来锁死。

---

## Q3：Phase 1 + Phase 2 合并是否合理？

**选 B：应分开，但不是回到原来的 Phase 1。**

memberships 已完成，旧 Phase 1 确实没有意义。但“CDN 化”本身太大：DB migration、pipeline、manifest API、客户端下载、校验、解压、导入、fallback、测试都在一个 PR，风险偏高。

我建议拆成：

1. **Phase 1a：后端可发布但 App 不消费**
   生成 examples package、写 manifest、校验 checksum、支持 dry-run、可回滚。
2. **Phase 1b：App 灰度消费**
   WordbookLoader 加 manifest 分支，但默认仍走 bundled；用 debug flag / remote flag 开启。
3. **Phase 1c：切默认路径**
   默认 CDN，bundled fallback 保留。

这样每一步都能独立验证，不会一次性把本地学习链路打穿。

---

## Q4：下一周单选推荐

**选 A：Phase 0.5 管线收口。**

理由：你现在的最大工程债是“发布动作不可重复、不可审计、不可安全删除”；先把 pipeline、dry-run、validate、GC 报告统一，后续 CDN 化才有可信地基。

---

## Q5：5 年长期项目的根本性误区

最大误区是：**把 stable_id 当成内容治理的全部答案。**

stable_id 只能解决“对象引用稳定”，不能解决“内容版本治理”。长期你需要的是：

```txt
content_release
- release_id
- package set
- target app version
- activation status
- rollback target
- QA result
- created_by / generated_by
- activated_at
```

否则未来会出现：用户 A 拿到 examples v7、audio meta v6、enrichment v4；排查 bug 时你无法复现用户看到的内容组合。对学习产品来说，**可复现的内容版本**比单个 stable_id 更重要。
