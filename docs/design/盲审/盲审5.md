已读文档。我的评审结论：**v0.2 的方向基本对，但它把“内容分发架构”当成一个 3-4 天功能来做，低估了发布原子性、回滚、客户端导入幂等和内容审核这四类工程风险。下一周不建议直接冲完整 CDN 化。**

## Q1：A.4 里哪个判断错了 / 漏了什么？

5 个问题本身都成立，尤其是“例句文本改动必须发 APK”和“音频分钟级、文本数天级”的不对称，是当前架构最真实的痛点。文档里明确说明 App 学习页例句来自 bundled JSON，而不是 cloud API；例句音频则走 API/CDN/本地缓存，两条链路的演进速度天然不一致。

但漏了一个更严重的问题：**内容发布缺少“原子版本边界”。**

现在方案讨论了 examples package、audio_assets、manifest、fallback、GC，但没有明确回答：

> 某次发布中，例句文本包 v5 已激活，但对应音频 assets 还没 ready，或者 manifest 激活成功但 CDN 文件上传失败，客户端应该看到哪个一致性视图？

这不是实现细节，而是内容平台的核心工程边界。建议把发布单位定义成 `content_release`，manifest 只暴露已通过校验的 release，而不是让 examples 包、audio meta、audio files 各自独立激活。

## Q2：是否该删 `example_book_memberships`？

我选 **C：折中，保留 schema 设计，但不立即建表。**

同意 v0.2 不立刻建表。当前 solo MVP、无真实用户，直接加 M:N 会增加 JOIN、运营决策、migration、API、测试成本，文档里列的代价是实的。

但我不同意把它简单判定为“未来真有再加，结构兼容”。因为 CET-4 / IELTS / 高中词书确实可能需要不同难度、不同语境、不同中文释义风格的例句。真正该保留的是**选择策略接口**，而不是马上建表。

建议现在做三件小事：

1. 在设计文档里保留 `example_book_memberships` 的未来 schema。
2. 当前代码不要依赖“一个 word 的所有 examples 对所有 book 永远等价”这个隐含假设。
3. examples package 生成器预留 `book_id` 过滤点，即使 v1 只是按 `word_book_memberships` 反查 examples。

这样未来加表时是扩展，不是推翻。

## Q3：Phase 1 + Phase 2 合并是否合理？

我选 **C：Phase 1 应重新定义为“Content Package Foundation”，而不是直接完整 CDN 化。**

v0.2 说 memberships 已 done，所以原 Phase 1 没意义，这点成立。文档也明确 Phase 1+2 要一次性做 migration、package 生成、manifest 发布、mobile state 表、WordbookLoader 新分支、API、下载校验、导入和测试。

问题是：这个范围对一个 PR 太大。失败面包括后端 schema、pipeline、CDN 文件、客户端下载、SQLite 导入、fallback、版本判断、弱网、离线、重试、回滚。任何一个失败都会让你很难定位问题。

我建议拆成：

**Phase 1：Content Package Foundation，不切流量。**
只做 manifest API、package build、checksum、content_package_state、导入器单测/集成测试，但 LearningPage 仍默认走 bundled。

**Phase 2：Examples CDN activation。**
开启 manifest-driven 分支，观察 fallback、失败重试、导入耗时，再决定 30 天后是否移除 bundled fallback。

这样不是“重构无产出”，而是先建立可验证的发布基座。

## Q4：下一周优先动哪一件事？

我选 **A：Phase 0.5 管线收口。**

一句话理由：**先把发布入口、校验和 stale GC 变成可重复、可 dry-run、可审计的流程，否则后面 CDN 化只是在混乱管线上叠更复杂的客户端状态机。**

文档里已经有 4 个脚本、8 步人工流程、6932 个 stale MP3 的事实，这说明当前最大风险不是“用户拿不到新例句”，而是“开发者自己很快无法安全发布内容”。

但我会把 Phase 0.5 的完成条件稍微加严：

* 不只是合脚本，还要产出一份 release report。
* `validate` 必须检查：examples stable_id、audio_assets target_id、source_text_hash、CDN 文件存在性、checksum。
* `publish-manifest` 必须最后一步执行，且只允许激活已验证 release。
* `gc-stale --dry-run` 输出要区分 orphan、superseded、deprecated grace window 内资源。

## Q5：长期 5 年视角的根本性误区

最大盲点是：**文档把内容包当“静态文件分发”，但长期它其实是“内容发布系统”。**

一旦项目长期做，真正难的不是 CDN 下载，而是这些问题：

* 谁批准一条例句进入 active？
* 一次 release 里哪些 examples、audio、enrichment 是同一批？
* 客户端 bug 需要回滚时，回滚 manifest 还是回滚包？
* 内容有争议或审核风险时，如何 revoke？
* 用户本地已经导入被撤回内容，是否需要 tombstone？
* 不同 app 版本能读哪些 package schema？
* TTS 音频和英文句子是否强一致？
* 内容质量问题能否追溯到 generator / prompt / source batch？

所以建议现在就引入一个轻量概念：`content_release`。不一定马上建复杂后台，但发布管线、manifest、GC、客户端 state 都围绕 release id 组织。这样 v0.2 不是“把 JSON 搬到 CDN”，而是搭起未来 5 年都能演进的内容发布骨架。
