## 1. 你这轮要做什么

你现在要做的，是在 **local-first + backup-first** 的前提下，增加一个 **最小 restore 能力**。

一句话：

> **让用户能够在明确知情、明确确认、明确风险提示的情况下，从已存在的 cloud backup snapshot 恢复到当前设备，但仍然不能把产品做成自动同步或多端合并系统。**

### 本轮允许做
1. 建立 restore use case / service / adapter
2. 拉取或读取“可恢复的云端备份快照”
3. 执行最小 restore apply
4. 建立 restore 前确认、restore 中、restore 成功、restore 失败的状态矩阵
5. 在设置页 / 我的页 / 数据与备份入口中增加 restore 的最小 gated 入口
6. 建立 restore 的测试与回归

### 本轮禁止做
1. 不做 auto restore
2. 不做 silent restore
3. 不做 full sync
4. 不做 background sync
5. 不做 multi-device merge
6. 不做 conflict auto-resolution
7. 不做 delete local data wizard（若未被单独 pin）
8. 不把 restore success 写成“所有设备已同步一致”
9. 不把 restore 做成默认主入口
10. 不顺手改主机制 / 副机制的既有业务规则

## 2. 你必须服从的事实边界

### 2.1 当前 P3.1 产品立场
P3.1 的正式名称是：

> **Local Progress + Cloud Backup**

当前冻结立场仍然是：

- **local-first**
- **backup-first**
- **manual backup**
- **不是 real-time sync**
- **不是 multi-device merge**
- **restore 是高风险动作，只能 gated 打开**

### 2.2 三类成功语义必须继续严格分开
你必须继续严格分开：

1. **local export success**
2. **cloud upload success**
3. **restore success**

本轮新增并实现的是第 3 类，但必须写硬：

- `restore success != sync success`
- `restore success != all devices consistent`
- `restore success != future auto-sync enabled`
- `has cloud backup != restore completed`
- `upload success != restore success`

### 2.3 restore 的准确角色
本轮 restore 是：

> **把某一份已存在的 backup snapshot 应用到当前设备本地运行态。**

它不是：
- 多端真相合并
- 云端成为 runtime truth
- 自动补齐所有端状态
- 历史版本时间线浏览系统
- 全量账户迁移平台

### 2.4 真相边界
restore 完成后：

- 当前设备的本地运行态会被恢复结果更新
- 这不等于“主业务真相源从此切到云端”
- 主机制关键业务规则事实仍服从 active BR / active versions
- 当前阶段云端依然只是 **backup container**

## 3. 这轮应该实现什么

## 3.1 Restore entry（最小入口）
restore 入口只能放在：
- 设置页
- 我的页
- 数据与备份分组
- 二级操作区

### 不能放在
- Today 主 CTA 中心
- 学习页 / 复习页 / Session 主流程
- 奖励结算层
- 喵喵主页核心互动区

### 入口形态
推荐：
- `从云端备份恢复`
- 或 `恢复备份`

但默认必须是：
- 二级入口
- 带风险说明
- 不比“立即备份”更突出

---

## 3.2 Restore pre-check（恢复前检查）
restore 执行前，至少要做以下最小检查：

1. 当前是否存在可恢复备份
2. 备份 schema version 是否受支持
3. 当前设备是否处于允许恢复的状态
4. 当前是否已有本地运行态数据
5. 是否需要用户二次确认

### 至少要有的结果分类
- `restorable`
- `not_restorable`
- `version_not_supported`
- `backup_not_found`
- `temporarily_unavailable`

不要直接点击按钮就恢复。

---

## 3.3 Restore confirmation（恢复前确认）
restore 是高风险动作，本轮必须有明确确认层。

确认层至少要告诉用户：

1. 这是把云端备份恢复到当前设备
2. 可能覆盖当前设备上的本地进度
3. 这不是实时同步
4. 恢复完成后，不代表其他设备也自动一致
5. 恢复前建议先手动备份当前设备（若产品已经具备此能力）

### 文案原则
允许：
- `将使用最近一次云端备份恢复当前设备数据`
- `这可能覆盖当前设备上的本地进度`
- `建议先手动备份当前设备，再继续恢复`

禁止：
- `一键同步所有设备`
- `恢复后将自动保持全平台一致`
- `恢复将自动解决所有冲突`

---

## 3.4 Restore apply
你需要建立 restore apply 的最小实现。

至少要回答：
1. restore 从哪里拿 snapshot
2. snapshot 如何解析
3. 哪些本地实体会被覆盖
4. 是否采用“整包替换”还是“有限替换”
5. 失败时如何回滚或至少不进入半成功态

### Room 4 当前推荐
优先采用：

> **整包、最小、明确范围的 restore apply**

也就是：
- 只恢复当前已进入 snapshot 范围的实体
- 不做局部 merge
- 不做复杂冲突解决
- 若失败，不让 UI 进入“看起来恢复成功”的假态

---

## 3.5 Restore state matrix
你必须把 restore 状态矩阵做清楚，至少包含：

### A. restore_available
- 有备份可恢复
- 可进入确认层

### B. restoring
- 主按钮 loading / disabled
- 不允许重复触发
- 显示中性文案：`正在恢复备份`

### C. restore_succeeded
- 可以展示：`恢复成功`
- 可以提示用户当前设备数据已更新
- **不能**展示：`已同步`

### D. restore_failed
- 显示失败状态
- 可展示重试或稍后再试
- 不能让界面停在“看起来成功”

### E. version_not_supported
- 告知当前备份版本暂不支持恢复
- 不要误导成网络错误

### F. no_backup_found
- 中性空态
- 不责备用户

### G. temporarily_unavailable
- 系统窗口态
- 中性提示
- 不写成用户操作错误

## 4. 文案与状态表达硬边界

### 4.1 允许的表达
- 可恢复
- 正在恢复
- 恢复成功
- 恢复失败
- 当前设备数据已更新
- 建议先备份当前设备

### 4.2 禁止的表达
- 已同步
- 所有设备已同步一致
- 自动同步完成
- 自动冲突解决完成
- 云端已成为当前真相
- 当前所有端都已恢复

### 4.3 一个必须写硬的原则
> **restore success 只表示“当前设备已完成恢复”，不表示“同步系统已成立”。**

## 5. 推荐执行顺序

### Step A — 接 restore pre-check
先做恢复前检查，不要先做 apply。

### Step B — 做确认层与高风险提示
把用户确认路径收清楚。

### Step C — 落 restore apply
只按最小范围恢复已进入 snapshot 的实体。
不要做 merge engine。

### Step D — 接设置页 / 我的页 restore 最小入口
入口必须是 gated 的，不抢主流程。

### Step E — 补失败 / 不支持版本 / 暂不可用状态
不要只做 happy path。

### Step F — 补测试并做回归
必须同轮补测试。

## 6. 你本轮必须补的测试

## A. Restore semantics tests
覆盖：
1. restore success 不等于 sync success
2. restore success 不等于 all devices consistent
3. has backup 不等于 restore completed
4. upload success 不等于 restore success

## B. Restore pre-check tests
覆盖：
1. 有可恢复备份
2. 无备份
3. 版本不支持
4. 暂不可用
5. 不允许直接跳过 pre-check 进入 apply

## C. Confirmation tests
覆盖：
1. restore 前必须二次确认
2. 风险说明正确显示
3. 没确认不能执行 restore
4. 文案中不出现“已同步 / 所有设备一致”

## D. Restore apply tests
覆盖：
1. restore 成功时本地数据被正确更新
2. restore 失败时不会停在假成功态
3. restore 过程中不可重复触发
4. restore 仅影响 snapshot 范围内实体
5. 不做额外 merge

## E. UI entry / state tests
覆盖：
1. restore 入口只出现在设置页 / 我的页 / 数据与备份区
2. Today 主链路没有 restore 主入口
3. `restoring / restore_succeeded / restore_failed / version_not_supported / no_backup_found / temporarily_unavailable` 状态都可见
4. 不出现“已同步”文案

## F. Existing flow regression tests
覆盖：
1. Today 主链路不受影响
2. 新词 / 复习 / Session / 签到现有流程不受影响
3. 既有副机制首页 / summary / reward 表达不被误污染
4. P3.1 入口不会压主学习 CTA
