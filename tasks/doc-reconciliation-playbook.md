# 文档对齐工作手册（Documentation Reconciliation Playbook）

> 本文件是给 Claude Code 的**完整任务说明书**，同时也是贯穿整个对齐过程的**共享参考文档**。
> 每次开新会话时，请先让 Claude Code 读一遍这份文件再开始工作。

---

## 0. 这是什么

本项目有 4 份文档：**BR（业务需求）**、**UI Spec（界面规格）**、**DB（数据库设计）**、**API（接口文档）**。
分别在docs/design目录下
过去几个开发阶段有改动没回写文档，现在代码领先文档。本次任务是**让文档追上代码**，为后续维护系统，开发新功能打好基础。

这不是开发任务，是**审计 + 技术写作**任务。

### ⚠️ 重要架构前提：本项目是**云端 + 手机本地端**双端架构

- **DB 两端都有**：云端有一套数据库，手机本地也有一套数据库（可能是 SQLite 或类似方案）。两端 schema 可能相同、可能不同、可能是子集关系——具体要看代码。
- **API 设计未知**：目前不确定 API 是怎么设计的（是纯云端 REST？还是有同步协议？本地是否也暴露某种"API"供 UI 调用？）。**Claude Code 必须在 Phase 0 就搞清楚这件事，不要假设。**
- **标注义务**：在所有文档中，凡是涉及 DB、API、数据流、存储的内容，**必须明确标注属于哪一端**。如果双端都有，要分别说明、并指出两端的差异或同步关系。

**标注约定**（在所有文档中统一使用）：

| 标签 | 含义 |
|---|---|
| `[云端]` | 仅存在于云端服务器 |
| `[本地端]` | 仅存在于手机本地 |
| `[双端]` | 两端都有且结构一致 |
| `[双端·差异]` | 两端都有但结构/行为不同——必须并列说明两边 |
| `[同步]` | 与两端之间的数据同步机制相关 |

章节、表格行、API 条目，只要涉及存储或数据流动，**都要带上这类标签**。

## 1. 最高原则（不可违反）

1. **绝对不改代码**。只读审计，唯一允许写入的目录是文档目录（见 §3）。
   - ❌ 不改 `.ts/.js/.py/.sql/.vue/.tsx` 等任何源码
   - ❌ 不跑 migration、formatter、lint --fix
   - ❌ 不"顺手"修 typo、不"顺手"补 comment
2. **代码是事实来源（Source of Truth）**。文档与代码冲突时，一律以代码为准。
3. **质量优先于速度**。宁可慢、宁可分批，也不要产出含糊、猜测、"大概是这样"的文档。
4. **不确定就标注，不要编造**。使用 `> ⚠️ TODO(待确认):` 前缀，说明不确定的原因和需要用户确认的具体问题。
5. **保持旧文档的结构和术语**。除非结构明显已不适用，否则不擅自重组章节；要改结构先提议、等确认。
6. **每个 Phase 结束后停下来等确认**。不要自动进入下一阶段。

## 2. 工作流程总览

```
Phase 0  →  Phase 1  →  Phase 2  →  Phase 3  →  Phase 4
 盘点        代码现状    差异分析    文档重写    交叉检查
 (侦察)      (采集)      (对比)      (产出)      (验收)
              ↑           ↑           ↑           ↑
           checkpoint  checkpoint  checkpoint  checkpoint
```

**每个 checkpoint 都必须停下来等用户确认，不要跨 Phase 连续执行。**

## 4. Phase 详解

### Phase 0 — 盘点（Reconnaissance）

**目标**：摸清家底，确认工作范围。

**Claude Code 要做的事**：
1. 扫描项目根目录，报告技术栈：前端框架、后端框架、DB、ORM、包管理器、monorepo 结构（如有）。
2. **双端架构侦察（本项目重点）**：
   - 识别云端代码和本地端代码的目录边界（是同一 repo 还是分开？是 monorepo 的不同 package 吗？）
   - 云端 DB 是什么？本地端 DB 是什么？分别在哪里定义 schema / migration？
   - 数据在两端之间是怎么流动的？找出所有疑似"同步"、"sync"、"pull"、"push"、"upload"、"download"、"merge"、"conflict" 相关的代码，汇报文件位置
   - API 层的真实样貌：是纯云端 REST/GraphQL？本地是否也有一层 service/repository 被 UI 当 API 用？是否存在同步专用的接口（和普通 CRUD 接口分开）？
   - 如果看不清楚同步机制，**明确报告"同步机制不清楚"**，不要猜。
3. 找到 4 份旧文档的位置和最后修改时间。如果找不到某一份，明确报告。
4. 报告代码大致规模：云端有多少 endpoint、本地端有多少 service、多少个 migration（云端/本地分别算）、多少个页面。
5. 提出本次对齐的目录方案（可基于 §3 微调）。
6. 列出任何"看起来很怪、需要先问清楚"的点（例如：两套并存的 API、废弃但未删除的 migration、注释掉的大段代码、两端 schema 明显对不上的字段）。

**产出**：一份简短的 `_reconciliation/README.md`，包含以上 5 项。

**🛑 Checkpoint 0**：等用户确认技术栈理解正确、目录方案 OK、没有盲区后，再进入 Phase 1。

### Phase 1 — 代码现状采集（Fact Gathering）

**目标**：从代码里客观地提取"当前系统实际是什么样"，**完全不参考旧文档**。

> 为什么不参考旧文档？因为一旦先读旧文档，认知就会被锚定，容易把代码"读成"旧文档描述的样子。必须先独立地从代码提取事实，再去对比。

#### 1a. DB 现状 → `current-db.md`

扫描范围：云端和本地端的 migration 文件、ORM model、schema 定义、seed 数据（仅用于推断用途）。

**本项目特殊要求——双端 DB 分别处理**：

文档必须**分成两大部分**：`## 云端数据库` 和 `## 本地端数据库`，分别完整列出每一端的 schema。不要合并成一份，哪怕两端看起来一样——看起来一样不代表真的一样。

对两端共有的表，**在每一端各写一次**，然后在该表的小节末尾加一个 `### 双端对比` 子节，列出字段层面的差异（本地端多了/少了哪些字段、类型是否一致、索引是否一致、默认值是否一致）。

如果两端完全一致，也要显式写一句 `> 与云端一致，无差异`，而不是省略。

每一端都必须列出：
- 所有表的**完整字段清单**（字段名、类型、nullable、默认值、注释）
- 主键、外键、唯一约束、索引
- 枚举类型及其取值
- 表之间的关系图（文字描述或 Mermaid）
- 明显的"软删除"、"多租户"、"审计字段"、"同步元数据字段"（如 `updated_at`、`sync_version`、`deleted_flag`、`dirty`、`last_synced_at` 等）等横切模式

**同步相关字段**要特别标出来并单独列一节 `### 同步元数据`——这些字段是理解整个同步机制的钥匙，不要混在普通字段里一笔带过。

格式要求：每张表一个小节，字段用表格呈现，表名旁边带上 `[云端]` / `[本地端]` / `[双端]` 标签。

#### 1b. API 现状 → `current-api.md`

扫描范围：云端路由/controller/handler/中间件、DTO/schema、本地端被 UI 调用的 service/repository 层、两端之间的同步代码。

**本项目特殊要求——先定义"API"是什么，再列清单**：

在动手列接口之前，先在文档最开头写一节 `## API 形态综述`，回答以下问题（基于 Phase 0 的侦察结果）：

1. 本项目实际存在几种"接口"？例如可能有：
   - 云端 REST/GraphQL 接口（UI 直接调用？还是只有同步层调用？）
   - 本地端的 service 层（被 UI 当 API 用）
   - 同步专用接口（批量 pull/push、增量同步、冲突解决）
   - 本地端暴露给 UI 的查询/命令接口（如果用了类似 Repository 模式）
2. 每种接口的**调用方向**是什么？（UI → 本地？UI → 云端？本地 → 云端？云端 → 本地（推送）？）
3. **数据在什么情况下走云端、什么情况下走本地？**（离线优先？先写本地再同步？读云端写本地？）
4. 鉴权/会话/token 机制是怎样的？本地是否有独立会话？

这一节是整份 API 文档的地基。如果这一节写不清楚，后面的 endpoint 清单就没意义——停下来问用户，不要硬写。

**分区列出接口**，按以下分组：

- `## 云端 API [云端]`：传统意义上的后端接口
- `## 本地端接口 [本地端]`：UI 调用的本地 service / repository（如果有这一层）
- `## 同步接口 [同步]`：两端之间的同步协议（这是最容易被忽略的一类，重点检查）

每个接口必须列出：
- 所在层（云端 / 本地端 / 同步）
- Method + Path（REST）或 函数签名（本地 service）
- 鉴权要求（公开 / 登录 / 特定角色 / 本地无需鉴权）
- 路径参数、Query 参数、Request Body（字段名、类型、是否必填）
- 成功响应结构
- 错误码和错误场景
- 依赖的 service / DB 表（反向追踪，并标注是哪一端的表）
- **调用者**：谁在调这个接口？（UI 的哪个页面？同步层？其它 service？）——这对理解架构至关重要

按资源或模块分组（例如 `/users`、`/orders` 分别成章），资源名旁边带上端点标签。

#### 1c. UI 现状 → `current-ui.md`

扫描范围：页面文件、路由配置、主要组件、状态管理。

必须列出：
- 所有路由 / 页面（path、页面用途一句话）
- 页面间的跳转关系
- 每个页面的主要交互元素（表单、列表、按钮、弹窗）
- 每个页面调用的接口——**必须标注该接口是云端 / 本地端 / 同步层**（与 1b 交叉）
- 明显的权限/角色分支
- **离线行为**：页面在离线状态下的可用性（完全可用 / 只读 / 不可用）——如果代码里看不出来，打 TODO

不要过度描述 CSS 和视觉细节——UI Spec 关心的是**结构和交互**，不是像素。

#### 1d. BR 现状 → `current-br.md`

BR 最难，因为它不是直接从代码能读出来的——它是**从 API + UI + DB 反推出的业务能力集合**。

必须列出：
- 系统支持的角色 / 用户类型
- 每个角色能做的主要业务动作（动词+对象）
- 主要业务流程（用户注册 → 下单 → 支付 → …）
- 业务规则（从代码里的条件分支、校验逻辑反推）
- 数据所有权和可见性规则

写 BR 时**最容易脑补**，请严格遵守"不确定就打 TODO"原则。

**🛑 Checkpoint 1**：用户会逐份 review 这 4 个 current-*.md。这是最关键的检查点——如果 Claude Code 对代码的理解是错的，越往后错得越远。用户确认后才能进入 Phase 2。

### Phase 2 — 差异分析（Diff）

**目标**：把"代码现状"和"旧文档"逐项比对，分类出所有差异。

现在才去读旧文档。针对每份文档生成 `diff-{br,ui,db,api}.md`，按四类组织：

| 类别 | 含义 | 处理方式 |
|---|---|---|
| 🟢 **新增** | 代码有、旧文档无 | 写入新文档 |
| 🔴 **删除** | 旧文档有、代码无 | **必须用户确认**——是真删除了？还是代码有 bug / 遗漏？ |
| 🟡 **修改** | 两边都有但不一致 | 以代码为准写入新文档，但用户要知情 |
| ⚠️ **不确定** | 代码写法模糊，业务意图不明 | **必须用户确认** |

每一条差异都要写清楚：**在哪里（文件+行号或章节）**、**旧文档怎么说**、**代码实际如何**、**建议动作**。

**🛑 Checkpoint 2**：用户会逐条 review 🔴 和 ⚠️ 两类。这是决策最密集的一步，可能要来回几轮。用户确认每一条的处理方式后才能进入 Phase 3。

---

### Phase 3 — 文档重写（Rewrite）

**目标**：基于 Phase 1 的事实 + Phase 2 的决策，重写 4 份文档。

**一次只写一份，写完一份 review 一份，再开始下一份。** 建议顺序：

```
DB  →  API  →  UI Spec  →  BR
(最客观)              (最主观)
```

从最客观的开始，因为 DB 几乎是硬事实；到 BR 时 Claude Code 已经对整个系统有完整认知，写业务描述才不会空洞。

**每份文档的结构要求**：
1. **文档头部**：版本号、生成日期、对齐依据的 git commit hash（如可得）
2. **变更摘要**：相对旧版的主要变化要点（不逐字 diff，5–15 条要点即可）
3. **正文**：保持旧文档的章节顺序和术语风格
4. **未决事项**：所有未解决的 `⚠️ TODO(待确认)` 集中列在文末，方便后续跟进

**写作风格要求**：
- 中文，术语与旧文档保持一致
- 字段定义、接口参数、表结构一律用**表格**，不用散文
- API 的 request/response 示例必须从代码里的真实 schema 生成，不得编造字段
- DB 的类型、默认值、nullable、索引必须和 migration/schema 字面一致
- 禁用模糊词：❌"可能"、"大概"、"应该是"、"通常"——要么写确定的，要么打 TODO

**🛑 Checkpoint 3 (×4)**：每写完一份文档停一次，用户 review 通过再开始下一份。

---

### Phase 4 — 交叉一致性检查（Cross-Check）

**目标**：4 份文档之间互相验证，找出系统性的不一致。

产出 `cross-check.md`，至少检查：

1. **BR → 实现**：BR 里提到的每个功能，能否在 UI / API / DB 里找到对应实现？
2. **API → 用途**：每个接口是否能在 UI 里找到调用点，或在 BR 里找到用途？孤儿接口要列出来，并标注属于哪一端。
3. **DB → 使用**：每张表、每个字段是否有接口或业务流在用？孤儿字段要列出来，并标注属于哪一端。
4. **UI → 后端**：UI 提到的每个交互是否都有对应的接口和 DB 支持？
5. **双端一致性（本项目专项）**：
   - 两端同名的表字段是否一致？不一致的要列出来（这可能是技术债，也可能是故意的设计）
   - 每一个"云端独有"的字段，是不会同步到本地、还是漏了？
   - 每一个"本地独有"的字段（尤其是同步元数据），用途是否清晰？
   - 同步接口覆盖的表集合 vs DB 里实际存在的表集合，有没有缺漏？（即"有这张表但没有同步逻辑"或反之）
   - UI 在离线状态下依赖的本地能力，是否都在本地端 DB / 接口中存在？

这一步**不是要修复所有不一致**——孤儿字段、废弃 endpoint 很可能是真实存在的技术债。这一步是把它们**显性化**，让用户知道项目里有哪些"暗礁"，方便后续决策。

**🛑 Checkpoint 4（最终）**：用户 review 交叉检查报告，决定哪些是真问题要开 ticket、哪些可以接受、哪些需要回头再改文档。

---

## 5. 质量 Checklist（每份文档交付前自检）

Claude Code 在每份文档写完、交给用户 review 前，请先自检以下项：

- [ ] 所有字段/接口/路由都能在代码里找到对应出处（可追溯）
- [ ] 没有从旧文档"继承"但代码里不存在的内容
- [ ] 没有使用"可能/大概/应该"等模糊词
- [ ] 所有不确定的地方都有 `⚠️ TODO(待确认)` 标记
- [ ] 术语和旧文档一致（或在变更摘要里明确说明术语变化）
- [ ] 表格格式统一、字段顺序一致
- [ ] 示例代码/JSON 是从真实 schema 生成，不是编造
- [ ] 文档头部有版本、日期、commit hash
- [ ] 变更摘要覆盖了所有重要变化
- [ ] 未决事项集中列在文末

## 6. 沟通约定

- **报告进度要精炼**：不要复述已经写过的内容，只说"做了什么、发现了什么、下一步建议"。
- **发现重大问题立即停下来问**：如果发现代码本身有 bug、有两套互相矛盾的实现、或有大段死代码，不要自己决定怎么写文档——停下来告诉用户。
- **不要批量提问**：一次提 1–3 个最关键的问题，等回答再问下一批。
- **用中文**，术语可保留英文。

## 8. 附录：常见陷阱

以下是这类任务中最容易出问题的地方，Claude Code 请特别注意：

1. **把注释当规格**：代码注释可能本身就过期了，不要把过期注释当成"业务意图"写进 BR。
2. **把测试当行为**：测试可能 skip 了、可能在测过时的行为，不要仅凭测试推断当前行为。
3. **忽略中间件和装饰器**：鉴权、限流、日志往往藏在装饰器或中间件里，容易漏掉。
4. **忽略数据库触发器和默认值**：业务逻辑可能藏在 DB 层，不只是应用代码里。
5. **把"能跑"当"是对的"**：代码能跑不代表符合业务意图，模糊时必须打 TODO。
6. **被旧文档带偏**：Phase 1 必须独立于旧文档进行，这一条再强调一次。
7. **假设两端 DB 一样**：看起来一样不代表真的一样。字段名一致但类型/默认值/索引不一致，是此类项目最常见的 bug 温床。必须字段级别逐一比对。
8. **把本地 service 当"前端代码"忽略掉**：在双端架构里，本地的 service/repository 层实际上扮演着 API 的角色，必须当成一类接口来记录，不要因为它"在前端目录下"就漏掉。
9. **忽略同步元数据字段**：`updated_at` / `version` / `dirty` / `deleted_flag` / `last_synced_at` 这类字段是同步机制的骨架，写 DB 文档时必须单独成节，不要混在业务字段里。
10. **假设所有数据都走同步**：可能有些表是"仅云端"（如审计日志）、有些是"仅本地"（如 UI 偏好设置）、有些是"双向同步"、有些是"单向下发"。不要默认一视同仁。
