# 实现步骤 TASKS

> **使用方法**：本文档是给 Claude Code 看的工作流程指南。每个 phase 都是一个独立的工作单位，**完成后必须停下等用户 review，再开始下一个 phase**。

> **重要原则**：phases 是有顺序依赖的。Phase 1 的产出（design tokens）会被 Phase 2-7 全部使用。Phase 2 的产出（共享资源和组件）会被 Phase 4-7 全部使用。**不要跳序，不要并行**。

---

## Phase 0：项目准备和技术栈确认

**目标**：在写任何代码之前，和用户对齐技术栈和项目结构。

**步骤**：
1. 检查代码库当前状态：
   - 项目里**已经存在什么**？是已有的代码库还是空目录？
   - 如果有已有代码，使用了什么技术栈、什么目录结构？
   - **找到旧版首页的代码位置**——它会作为后续"原版"tab 的目标
2. 如果代码库是空的或有重大缺失，向用户提出技术栈建议（React Native / Flutter / Web 等），等用户决定后再继续
3. 如果代码库已有技术栈，使用同一栈，**不要引入新框架**

**产出**：一份简短的报告（写在聊天里，不要创建文件），包含：
- 当前代码库状态
- 旧版首页的位置（具体路径）
- 推荐的技术栈和理由
- 推荐的目录结构

**Checkpoint**：等用户确认技术栈和目录结构后才能进入 Phase 1。

**Stop and ask 触发条件**：
- 找不到旧版首页代码
- 用户没有指定技术栈而代码库是空的
- 旧版首页用了一个和新设计冲突的依赖（例如旧版用 Vue，新设计你想用 React）

## Phase 1：设计 Tokens

**目标**：把 SPEC 第 3 节的所有设计 tokens 转化成代码里可引用的常量。

**步骤**：
1. 创建一个 tokens 文件（位置和格式由技术栈决定）：
   - Web/CSS：`src/styles/tokens.css` 或 `src/theme/tokens.ts`
   - React Native：`src/theme/tokens.ts`
   - Flutter：`lib/theme/tokens.dart`
2. 把 SPEC 第 3.1 节的所有颜色作为命名常量
3. 把 SPEC 第 3.2 节的字体堆栈和字号阶梯作为常量
4. 把 SPEC 第 3.3 节的圆角值作为常量
5. 把 SPEC 第 3.4 节的间距值作为常量
6. **不要添加 SPEC 没有的颜色或值**——如果发现某个 token 不够用，停下来问

**产出**：一个 tokens 文件，所有值与 SPEC 第 3 节 100% 一致。

**Checkpoint**：把文件内容贴出来给用户看一遍，确认所有 hex 值无误。

**Self-review 要点**：
- 每一个颜色 hex 是否与 SPEC 完全一致
- 字重是否只有 400 和 500
- 是否引入了任何 SPEC 没有的值

## Phase 2：共享 SVG 资源

**目标**：把 SPEC 第 4 节的所有 SVG 资源做成可复用组件。

**步骤**：
1. 创建以下组件，每个 SVG 一个独立组件：
   - `MochiLarge` — 4.1 节的大 Mochi（用于 Mochi 页主插画）
   - `MochiAvatar` — 4.2 节的小 Mochi（用于头像、落款等）
   - `PawPrint` — 4.3 节的爪印（接受 color 和 opacity props）
   - `IconHome` / `IconBooks` / `IconMochi` / `IconStats` / `IconProfile` — 4.4 节的 5 个 tab bar 图标
   - `IconLegacy` — 5.1.6 节的原版 tab 图标（线性档案夹）
2. 每个图标组件接受 `selected: boolean` prop（除 IconLegacy，它始终是同一种状态）
3. SVG 内部坐标和路径**完全照搬 SPEC，不要修改**

**产出**：一个 components/icons 目录（或同等位置），包含上述所有组件。

**Checkpoint**：渲染一个测试页面，把所有图标按 selected/not-selected 两种状态显示出来，让用户看一眼。

**Self-review 要点**：
- 所有 SVG 路径数据与 SPEC 完全一致
- 图标在小尺寸（22-26px）下渲染清晰
- Mochi 头像 SVG 内部颜色未被修改（这是品牌资产）

---

## Phase 3：共享组件

**目标**：实现 SPEC 第 5 节的共享组件（卡片、列表、tab bar）。

**步骤**：
1. 实现卡片组件（5.2 节的 4 种）：
   - `Card.Filled` — 米色填充卡
   - `Card.Outlined` — 描边卡
   - `Card.Hero` — 紫色 hero 卡（接受 children 和右下角 PawPrint 选项）
   - `Card.MochiWarm` — Mochi 暖色卡
2. 实现列表组组件（5.3 节）：
   - `SettingsGroup` — 设置组容器
   - `SettingsRow` — 单个列表项
3. 实现 Tab Bar 组件（5.1 节）：
   - 接受当前选中的 tab 名作为 prop
   - 包含 6 个 tab：首页 / 词书 / Mochi / 统计 / 我的 / 原版
   - 第 6 个 tab "原版" 视觉上明显区别（按 5.1.6 节规格）
   - 触控目标最小 44×44px
4. **不要给任何组件加 hover 阴影、scale 动画、过渡效果**（除非 SPEC 明确要求）

**产出**：一个 components/ui 目录，包含上述组件。

**Checkpoint**：渲染一个测试页面，并排显示这 4 种卡片和一个完整 tab bar，让用户看一眼。

**Self-review 要点**：
- 所有圆角值与 SPEC 一致（16/18/22）
- 没有添加任何阴影、渐变、动画
- Tab bar 第 6 个 tab 视觉上明显是"附加项"而不是"和其他 5 个平等"
- 触控目标足够大

## Phase 4：首页（SPEC 第 6.1 节）

**目标**：实现首页所有元素。

**步骤**：
1. 顶部问候 + 当前词书 + 用户头像区
2. **Mochi 打卡条**（使用 Card.MochiWarm + MochiAvatar）
3. **主 CTA "继续学习"**（使用 Card.Hero + 右下角 PawPrint，opacity 0.18，white）
4. 数字卡组（本书进度 / 错词本，使用 Card.Filled）
5. 5 分钟快速复习入口（使用 Card.Outlined）
6. 集成 Tab Bar，选中"首页"
7. 所有点击行为按 SPEC 6.1.x 实现，跳转目标暂时可以是空函数 + console.log

**重要数据规则**：
- 问候语按 6.1.2 节的时间段动态变化
- "Mochi 等了你 N 小时"按 6.1.3 节的逻辑计算
- 数据先用 SPEC 第 8.3 节的占位值

**产出**：一个完整的首页路由 `/`。

**Checkpoint**：
1. Claude Code 自己按 SPEC 第 10 节做一遍 self-review，把结果写出来
2. 用户在浏览器/模拟器里看实际效果
3. 用户对照 SPEC 第 6.1 节逐项检查是否符合

**Stop and ask 触发条件**：
- 任何 SPEC 没明确规定的视觉细节
- 任何点击行为不知道跳转到哪里（先暂停问，不要写占位页）

## Phase 5：Mochi 页（SPEC 第 6.2 节）

**目标**：实现 Mochi 页所有元素。

**步骤**：
1. 顶部信息区（Mochi 名 + 陪伴天数 + 羁绊 pill）
2. 大 Mochi 插画区（使用 MochiLarge），包含：
   - 对话气泡（绝对定位）
   - "+1 张新照片"浮层（仅有新照片时显示）
   - "轻轻戳一下试试"引导提示（一次性，本地存储记录）
3. 进度条
4. Mochi 主 CTA（玫红色卡，文案严格按 6.2.5）
5. 4 个次级入口：换装 / 房间 / 零食柜 / 日记
   - 零食柜带数字角标显示小鱼干余额
   - **4 个入口的目的地都是占位（点击触发 stop-and-ask）**，因为子页未设计
6. 日记预览卡
7. 集成 Tab Bar，选中"Mochi"

**重要纪律**：
- Mochi 永远不会有负向状态（不饿、不病、不消失）
- 文案永远是温柔陈述，不是焦虑勒索
- 整个 MochiLarge SVG 是可点击的（点击触发动画占位，先用 console.log）
- 引导提示一次性消失逻辑必须实现

**产出**：一个完整的 Mochi 页路由 `/cat`。

**Checkpoint**：
1. Self-review
2. 用户看效果
3. 特别确认 4 个次级入口的"未实现"状态对用户友好（点击不是闪退，是给一个明确反馈）

**Stop and ask 触发条件**：
- 4 个次级入口的目的地（确认是不是真的要做"待开发"提示，还是先空着）
- Mochi 互动动画的具体形式

## Phase 6：统计页（SPEC 第 6.3 节）

**目标**：实现统计页所有元素。

**步骤**：
1. 页面标题
2. 大数字 Hero 卡（已掌握 1240）
   - **必须用"已掌握"叙事，绝对不能用"还差多少"**
   - 右下角 PawPrint，color `#6B4FA8`，opacity 0.22
3. 三个核心指标卡（连续 / 本周 / 记忆率）
   - **"连续"用珊瑚色 #993C1D，其他两个用暖紫 #6B4FA8——这个区分是有意的**
4. 12 周热力图（SVG，3×12 方格，rx=3）
   - **不能用红绿配色**
5. 本周亮点卡（绿色）
   - **如果没有正向数据，整个卡片隐藏**，不要硬塞负面消息
6. "需要关注"列表
7. **Mochi 落款**（小头像 + 斜体文字，居中，不可点）
8. 集成 Tab Bar，选中"统计"

**重要纪律**：
- 统计页是数据页，永远是中性陈述
- "需要关注"措辞用"建议"和"按当前进度"，不要施压
- Mochi 落款是签名不是按钮，绝对不要让它变成可交互卡片

**产出**：完整统计页路由 `/stats`。

**Checkpoint**：Self-review + 用户检查。特别确认 Mochi 落款的视觉权重正确（要被看到，但不显眼）。

## Phase 7：我的页（SPEC 第 6.4 节）

**目标**：实现我的页所有元素。

**步骤**：
1. 用户身份区（默认头像是 Mochi）
2. 当前词书卡
   - 右上角"切换 →"用 #6B4FA8 加粗（页内唯一带颜色的高频入口）
3. 设置组：学习（4 项）
4. 设置组：数据（2 项）
5. 设置组：关于（2 项）
   - 版本号不可点
6. 集成 Tab Bar，选中"我的"

**重要纪律**：
- 副文必须是用户的成就，不能是 Mochi 的状态
- 不要加任何 SPEC 没有的设置项（特别是邀请好友、签到、会员中心、评分这类）
- 复习算法这一项必须露出，不要藏

**产出**：完整我的页路由 `/profile`。

**Checkpoint**：Self-review + 用户检查。

## Phase 8：原版 tab 集成（SPEC 第 5.1.6 节）

**目标**：把已有的旧首页作为第 6 个 tab "原版" 暴露出来。

**步骤**：
1. 在路由系统里添加 `/legacy` 路由，指向**已经存在的旧首页代码**
2. **绝对不要重写、重构、修改、美化这套旧 UI**
3. 在旧首页顶部（或它的容器外层）加一行 dev-only 警告横幅（按 5.1.6 节规格）
   - 用环境变量控制，**生产构建时隐藏**
4. 确认 Tab Bar 切换到这个 tab 时正确显示旧首页
5. 确认从旧首页的入口（如果有的话）能跳转回新设计的 4 个页面之一（或者保持原样不动）

**重要纪律**：
- 旧首页代码是只读的——你只能围绕它做最小集成
- 如果集成时遇到旧代码冲突（比如它依赖的全局样式和新设计的 tokens 冲突），停下来问，**不要修改旧代码也不要修改新 tokens**

**产出**：6 个 tab 全部能正常切换，原版 tab 显示旧首页。

**Checkpoint**：
- 用户从每个 tab 切到原版，再切回，确认行为正常
- 用户确认旧首页**完全没被改动**

**Stop and ask 触发条件**：
- 找不到旧首页代码
- 旧首页和新代码有冲突
- 旧首页的全局样式污染了新页面（这种情况很常见，必须问怎么解决）

---

## Phase 9：最终验收

**目标**：整体走查，确保 4 个新页面 + 原版 tab 都符合 SPEC。

**步骤**：
1. 按 SPEC 第 10 节的验收标准逐项检查每一个新页面
2. 写一份 self-review 报告，包含：
   - 每个页面是否通过像素级检查
   - 每个页面是否通过行为检查
   - 设计纪律是否被严格遵守
   - 整体萌度感受是否符合"5 分"目标
3. 列出**所有未实现 / 待补 / 占位**的内容，给用户一份明确的清单
4. 列出**任何你做了但和 SPEC 略有偏差**的地方（如果有的话），并说明原因

**产出**：一份 self-review 报告 + 待补清单。

**Checkpoint**：用户看完所有 5 个 tab，给最终反馈。

---

## 整体纪律回顾

在每个 phase 开始之前，回顾这 5 条：

1. **不要漂移** — 严格按 SPEC，不要"优化"
2. **不要补全** — SPEC 第 9 节的待补内容停下问
3. **不要跳序** — phases 有依赖关系，按顺序做
4. **不要静默决定** — 不确定就停下问
5. **不要修改原版** — 原版 tab 的旧代码是只读的

## 异常处理

如果遇到以下情况，**立即停下来告诉用户**：

- SPEC 内部有矛盾（比如两个地方写的颜色不一样）
- SPEC 没规定但你必须决定的事
- 你想违反 SPEC 第 8.8 节的某条纪律
- 你发现某个设计在技术上无法实现
- 你不确定旧首页代码该怎么集成

**停下来不是失败，是负责任**。把没想清楚的事情包装成决策提交，才是失败。
