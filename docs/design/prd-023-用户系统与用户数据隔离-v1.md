Room 1 判断：**需求 23 是大需求，而且是核心地基需求。**

它不是简单“加登录页”，而是：

> **给整个系统加用户身份边界，让每个用户只看到、只修改、只备份、只恢复自己的设置、学习进度、FSRS 规划、复习记录、奖励、猫猫和所有账号相关数据。**

当前项目里已经有“账号与基础同步”的初始口径：支持游客、登录 / 绑定、本地进度保存、手动云备份，并且学习数据、签到事实、奖励事件需要与 `user_id` 绑定。 但当前 API 现实仍是“无鉴权 / dev mode / 单用户开发态”，所以需求 23 的本质是把系统从**单用户开发态**推进到**账号隔离态**。

下面是 Room 1 改写后的需求。

---

# 需求23：用户系统与用户数据隔离 v1

## 1. 需求目标

为背单词喵喵 App 增加用户系统，使每个用户拥有独立的账号、设置、学习数据、FSRS 复习规划、奖励数据、猫猫数据和所有账号相关数据。

核心目标：

```txt
不同用户的数据必须隔离。
同一用户的数据必须能被稳定识别。
游客数据必须能在绑定账号后保留。
登录、退出、切换账号不能造成数据串号、丢失或覆盖。
```

一句话：

> **系统内所有“属于某个用户”的数据，都必须归属到明确 user_id。**

---

## 2. 本轮定位

本轮不是做复杂社交账号体系，也不是直接做 full sync。

本轮重点是：

```txt
账号身份 + 用户数据归属 + 本地/云端用户隔离 + 游客转正式用户
```

当前项目仍明确不做实时双向同步、多设备自动合并、登录后静默云端覆盖本地进度。 所以需求 23 不能偷偷变成 full sync 需求。

---

## 3. 本轮做什么

## 3.1 用户身份系统

支持以下用户状态：

```txt
1. 游客用户
2. 已注册 / 已登录用户
3. 游客绑定后的正式用户
4. 退出登录后的未登录状态
```

最低功能包括：

```txt
注册
登录
退出登录
游客模式进入
游客绑定账号
获取当前用户状态
```

---

## 3.2 每个用户有自己的设置

以下设置必须按用户隔离：

```txt
daily_goal
active_wordbook
学习偏好
复习偏好
发音偏好
界面偏好，如果后续有
备份状态，如果和账号绑定
```

例如：

```txt
用户 A 的 daily_goal = 30
用户 B 的 daily_goal = 50

切换到用户 A，只显示 30
切换到用户 B，只显示 50
```

不得出现：

```txt
用户 A 改了 daily_goal，用户 B 也被改了
```

当前 PRD 已要求每个用户同一时间应有一个当前 active 学习词库，切换词库后今日页目标口径同步更新。 需求 23 要把这个规则从“设备设置”推进到“用户设置”。

---

## 3.3 每个用户有自己的学习数据

以下学习数据必须按用户隔离：

```txt
单词学习进度
新词学习记录
复习记录
今日新词 served 记录
今日目标完成状态
学习 Session
签到记录
learning_day
streak
统计数据
```

用户 A 学过的词，不能出现在用户 B 的已学进度里。

用户 B 的复习任务，不能污染用户 A 的复习队列。

---

## 3.4 每个用户有自己的 FSRS 规划

FSRS 相关数据必须按用户隔离，包括：

```txt
card_states
review_logs
每个 word 的 stability
每个 word 的 difficulty
due 日期
last_review
rating history
本地复习规划状态
```

规则：

```txt
同一个 word_id，在不同用户下必须有不同的 FSRS 状态。
```

例如：

```txt
用户 A 对 abandon 很熟，下一次 20 天后复习
用户 B 第一次学 abandon，1 分钟后复习
```

这两个状态不能混在一起。

当前长期 DB 目标中也已经把 `card_states` 定位为 FSRS 卡片调度，并把本地 review logs 定位为 INSERT-ONLY、供 FSRS optimizer 使用的本地运行态数据。 需求 23 要补硬：这些运行态数据必须带用户边界。

---

## 3.5 每个用户有自己的奖励与猫猫数据

以下副机制数据必须按用户隔离：

```txt
coins
fish treats
EXP
reward ledger
pet profile
猫猫状态
家具布局
inventory
equipment slots
purchase records，如果未来有
feed events
```

规则：

```txt
副机制只能消费当前用户自己的主机制事件。
```

不得出现：

```txt
用户 A 学习后，用户 B 的猫猫获得奖励
用户 A 买的家具，出现在用户 B 的房间
```

---

## 3.6 游客数据绑定

用户可以先以游客身份使用 App。

当游客注册 / 登录并绑定账号时：

```txt
游客本地学习数据
游客 FSRS 规划
游客设置
游客奖励
游客猫猫数据
```

需要迁移到正式账号下。

绑定成功后：

```txt
游客数据不丢失
正式账号继续使用原游客进度
不会重新开始
不会生成第二份重复进度
```

---

## 3.7 退出登录与切换账号

退出登录后：

```txt
不得继续展示上一个用户的学习数据
不得继续使用上一个用户的 token
不得继续提交到上一个用户账号
```

切换账号后：

```txt
当前用户上下文必须切换
首页、学习页、复习页、设置页、猫猫页都必须读取新用户数据
```

如果当前设备没有该用户的本地数据：

```txt
进入该用户的空状态 / 初始化状态
不得复用上一个用户数据
```

---

## 4. 本轮不做什么

本轮不做：

```txt
1. 不做实时双向同步
2. 不做多设备自动合并
3. 不做 card-level conflict merge
4. 不做登录后自动用云端覆盖本地
5. 不做复杂第三方登录矩阵
6. 不做社交关系
7. 不做好友系统
8. 不做排行榜
9. 不做家庭账号 / 多成员账号
10. 不做管理后台
11. 不做复杂权限系统
12. 不做付费订阅账号体系
```

特别写硬：

> **登录成功 ≠ 自动同步完成。**
> **备份成功 ≠ 多设备一致。**
> **恢复成功才会改变当前设备本地数据。**

当前 DB 文档也明确要求区分 backup upload success、snapshot fetch success、restore apply success，并且当前不做 real-time sync、background sync、多设备 merge、partial restore 等能力。

---

## 5. 数据归属规则

## 5.1 必须属于用户的数据

以下数据必须有明确用户归属：

```txt
settings
user_book_settings
study_attempts
review_attempts
user_word_progress
card_states
local_review_logs
daily_goal_progress
session_records
check_in_records
learning_day_facts
streak_records
reward_source_events
reward_ledger
settlements
secondary_wallets
pet_profiles
feed_events
inventory_items
equipment_slots
purchase_records
backup snapshots
user notes
favorite examples
家具布局
```

## 5.2 不属于单个用户的数据

以下数据是公共内容层，不属于某个用户：

```txt
wordbooks
words
word_entries
word_book_assignments
example_sentences
audio_assets
word_forms
word_relations
word_phrases
morpheme_entries
word_morpheme_matches
```

这些内容可以被所有用户共享。

但用户对这些内容产生的行为必须属于用户，例如：

```txt
某个用户是否学过这个 word
某个用户是否收藏这个 example
某个用户对这个 word 的 FSRS 状态
某个用户对这个 word 的笔记
```

## 6. 核心业务规则

## Rule 1：当前用户上下文必须唯一

App 任意时刻只能有一个 active user context。

```txt
current_user_id = 当前所有用户数据读取和写入的唯一归属
```

不得出现：

```txt
页面 A 用用户 A
页面 B 用用户 B
提交接口用用户 C
```

---

## Rule 2：所有写操作必须绑定当前用户

以下行为必须绑定当前用户：

```txt
学习提交
复习提交
FSRS 更新
daily_goal 修改
active_wordbook 修改
签到
Session start / finish
奖励结算
猫猫数据更新
家具保存
备份上传
恢复应用
```

---

## Rule 3：退出登录后不得继续写入旧用户

退出登录后，如果用户继续使用游客模式，则必须进入新的游客上下文。

不得继续把行为写到旧登录用户。

---

## Rule 4：游客绑定不得丢数据

游客绑定正式账号时，必须保留游客本地数据。

如果发生失败：

```txt
游客本地数据不得被清空
游客本地数据不得被半迁移
用户需要能继续使用原游客数据
```

---

## Rule 5：用户切换不得串数据

用户 A 退出后，用户 B 登录：

```txt
首页读取用户 B 数据
学习页读取用户 B 数据
复习页读取用户 B 的 FSRS / review queue
设置页读取用户 B 设置
猫猫页读取用户 B 猫猫状态
```

用户 A 的数据不得出现在用户 B 视图中。

---

## Rule 6：本轮仍保持本地优先 + 手动备份边界

需求 23 不改变当前 P3.1 / P3.2 的大边界：

```txt
本地仍是当前设备运行态主真相
云端备份仍是 backup container
不默认做实时同步
不默认做自动 merge
不默认登录后覆盖本地
```

当前主机制 PRD 已写明本地进度是运行态主真相，云端当前只承担备份容器职责。

---

## 7. 页面需求

## 7.1 登录 / 注册页

最低支持：

```txt
邮箱注册
邮箱登录
游客进入
```

可选：

```txt
忘记密码
验证码登录
第三方登录
```

本轮可先不做第三方登录。

---

## 7.2 我的页 / 设置页

需要展示：

```txt
当前账号状态
游客 / 已登录
用户昵称或邮箱
绑定账号入口
退出登录入口
备份入口
最近一次备份状态
```

游客状态下需要提示：

```txt
绑定账号后，可以更安全地保留学习进度
```

但不要制造强迫感。

---

## 7.3 退出登录确认

用户点击退出登录时，需要确认。

提示重点：

```txt
退出后，本设备将不再显示当前账号数据。
如未备份，重新安装或清除本地数据可能导致进度丢失。
```

不做恐吓式文案。

---

## 8. 异常状态

必须处理：

```txt
注册失败
登录失败
token 过期
网络失败
游客绑定失败
退出登录失败
当前用户不存在
本地数据迁移失败
备份上传失败
恢复失败
```

原则：

```txt
失败不能清空本地数据
失败不能切错用户
失败不能静默吞掉
失败要给用户明确提示
```

---

## 9. 验收标准

## 9.1 账号基础验收

1. 用户可以游客进入。
2. 用户可以注册账号。
3. 用户可以登录账号。
4. 用户可以退出登录。
5. 用户可以从游客绑定为正式账号。
6. 退出登录后，不再显示旧用户数据。

## 9.2 用户设置隔离验收

1. 用户 A 设置 `daily_goal = 20`。
2. 用户 B 设置 `daily_goal = 50`。
3. 切回用户 A，仍显示 20。
4. 切回用户 B，仍显示 50。
5. active wordbook 同理隔离。

## 9.3 学习数据隔离验收

1. 用户 A 学习 abandon。
2. 用户 B 登录后，abandon 不应显示为用户 B 已学。
3. 用户 B 的今日目标、复习任务、统计数据不受用户 A 影响。

## 9.4 FSRS 隔离验收

1. 用户 A 对 abandon 评分后生成 FSRS 状态。
2. 用户 B 第一次学习 abandon 时，应是独立 FSRS 状态。
3. 用户 A / B 的 due、stability、difficulty 不互相影响。

## 9.5 游客绑定验收

1. 游客学习 10 个词。
2. 游客绑定账号。
3. 绑定后这 10 个词仍保留。
4. FSRS 状态仍保留。
5. 设置仍保留。
6. 奖励和猫猫状态仍保留。

## 9.6 退出 / 切换账号验收

1. 用户 A 登录并学习。
2. 退出用户 A。
3. 登录用户 B。
4. App 所有页面不显示用户 A 的数据。
5. 用户 B 的操作不会写入用户 A。

## 9.7 安全验收

1. 未登录请求不能访问需要登录的云端用户数据。
2. 用户 A 不能通过接口访问用户 B 的数据。
3. 所有 `/me/*` 接口只能返回当前登录用户的数据。
4. token 过期后不能继续提交旧用户数据。
