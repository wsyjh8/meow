## 总体观察

文档本身的工程质量很高：Part A 有数字和路径而非主观叙述，Part B 每个决策都引用 v0.3.0 §X.X.X，Part C 主动列反方避免 echo chamber。这种 "design doc + decision record" 的写法已经是工业级的。

但**正因为质量高**，下面挑出来的几个点都是隐性的、被掩盖在"看起来已经决策完毕"的表象下的结构性问题。

---

## 观察 1：删除 `example_book_memberships` 加深了一个隐性约束，这是个埋着的雷

`stable_id = sha256_24(canonical_json([word_id, normalize_text(en)]))`

这个公式隐含一个语义假设：**(word_id, normalize_text(en)) 是例句的唯一身份**。

v0.2 删 `example_book_memberships` 后，例句池变成"单词级共享池"。当前 OK，但作者说自己反方观点 #9 "难度分级是真需求"——只是判定 YAGNI 不做。问题是，未来真要做时会撞到这个公式：

如果要"abandon 在 CET-4 用一句简单例句、在 GRE 用一句复杂例句"，结构上有三条路：
- (a) `examples` 加 `book_id` 进 PK——破坏 stable_id 算法
- (b) 加 `examples` 加 `difficulty` 列，多条记录可以 (word_id, en) 相同但 difficulty 不同——**直接撞 PK 冲突**，因为 stable_id 一样
- (c) 维持 1:N，靠选题层（不在 examples 里）按 book 过滤——意味着 examples 永远是"全集池"，发布粒度永远不能按书细分

也就是说，v0.2 现在锁定的 stable_id 算法**让未来加难度分级必须做不兼容算法升级**。作者把这归为 "未来真有再加，结构兼容"——但**算法不兼容**，不是"加张表"那么简单。

**建议**：要么现在就把 stable_id 算法升级为 `sha256_24([word_id, normalize_text(en), scope])`，scope 当前为空字符串（向后兼容）；要么在 examples 加 `stable_id_version` 列，为未来算法演进留路径。当前 v0.2 既不做也不留路径，这是 5 年项目最贵的那种债。

## 观察 2：`content_hash` 列的语义没定义，这是包变更检测的核心

§B.4.4 加了 `content_hash VARCHAR(64)`，但全文没说它是什么的 hash：
- `sha256(en)`？那它和 stable_id 信息冗余（stable_id 已经是 en 的 hash 截断）
- `sha256(en + cn + sense_label + difficulty)`？那它能用作"中文翻译变了"的检测
- `sha256(jsonl 整行)`？那它是 row-level integrity check

这三种语义对应三种用途，**对客户端 cache 失效逻辑的影响完全不同**。如果客户端用 content_hash 判断"我本地这条要不要重新覆盖"，那它必须包括所有可变字段（包括 cn）；如果只用作 row integrity，那它可以只包 en。

文档对 manifest 包级 checksum 写得很清楚（`content_manifest.checksum_sha256`），但**行级别变更检测没明确**。修一句翻译的时候，客户端怎么知道这一条要更新而不是全包重导？或者每次包变化都全量重导？

后者在小词书可以接受，但 §B.10 的"30 天后移除 bundled"意味着新装用户首启就要拉**完整包**——如果未来包大到 50MB（含翻译扩展），这是个 UX 问题。

**建议**：明确 content_hash 的输入字段集合，进 §B.4.4 说明，并加 fixture 测试。否则 6 个月后另一个开发者看不出来要不要把它纳入客户端 diff 逻辑。

## 观察 3：bundled fallback "30 天后删除"是个伪命题

§B.10 完成条件第 3 条：bundled fallback 保留至上线 + 30 天，之后从 APK 移除。

这有两个具体问题作者没说清楚：

**问题 a**：30 天后从 APK 移除的方式是发新 APK。也就是说"删 fallback"动作本身就是一次发版。**那一刻 CDN 可用性 = 新装用户首启可用性**。MVP 阶段 mock CDN，到时候真 CDN 用什么、SLA 多少、首启失败怎么处理——没说。

**问题 b**：fallback 删除后，**永久弱网 / 偏远地区 / 没有 4G 的用户**首启永远拉不到例句。§C.1 反方观点 #1 提了，作者承认"fallback 删除后无解"——但这就是默认接受了一类用户体验断崖。

更稳的设计是 **always-bundled-minimum-set**：APK 永远 bundle 第一本词书的极简包（可能是当前 5.6MB 的 1/10），保证全离线场景首启可用。CDN 包是增量。这样既减小 APK，又不放弃离线兜底。

不是说必须现在做，而是 §B.10 的"30 天后删 fallback"应该改成"30 天后将 fallback 缩为 minimum-set"，明确长期形态。

## 观察 4：manifest 是多包的，但没有 manifest set 一致性约束

发布顺序考虑这个时序：

1. publish `examples-zk@v5` → manifest 写好
2. publish `audio_meta-zk@v5` → 还没写
3. App 看到 examples-zk@v5 拉了新包
4. 用户播放新例句音频 → 还在 v4 audio_meta，不一定有对应 audio_assets

虽然 stable_id 是英文绑的，新例句的 stable_id 在新 audio_meta 才有对应 audio_assets——**publish 顺序敏感**。

§B.7.3 说"发布顺序固定：包生成 → manifest publish → stale GC"，但这个固定顺序是**单包内部**的；多包之间（examples-zk 和 audio-meta-zk）的活性约束没在 manifest 协议里建模。

5 年视角下这必然出问题（多人发布、并发、回滚某一包）。

**建议**：`content_manifest` 加 `manifest_set_id` 概念，或者 `compatible_with_packages: ["audio-meta-zk@v5"]` 字段。客户端拉 examples-zk@v5 时确认其依赖的 audio-meta-zk@v5 也 active 才升级。否则版本错位是必然事件。

## 观察 5：6932 stale 不是缺 GC，是缺生命周期状态机

§A.4 问题 3 把 6932 stale 归为"管线缺 GC"。但根因是：**每次 LLM 改例句英文 → 新 stable_id → 新 audio_id → 旧的成孤儿**。一周改 100 句例句就有 100 个孤儿，不是"加个 GC 命令"能根治的。

正确的设计是 audio_assets 状态机：
```
active → (新版本 publish) → superseded (start grace window)
       → (grace 过期 + 无客户端引用) → eligible_for_gc
       → (gc dry-run 确认) → deleted
```

每个状态有 `transitioned_at`，GC 是 query 状态机，不是 set diff。

§B.8 描述了 GC，但**完整生命周期没显化**。当前实现是"看 audio_assets 表里没有就是孤儿"，这是错的——publish 流程的中间态、灰度回滚态、deprecated grace window 都不能误判为孤儿。

Phase 0.5 应该不只合并脚本，而是**实现 audio_asset 状态机**。如果只把 4 个脚本合到 pipeline.py 但状态判断逻辑还是 set diff，问题没解决。

## 观察 6：Phase 1+2 单 PR 跨 3 仓 7 层，blast radius 太大

合并 PR 触及：PG migration / API endpoint / drift schema / WordbookLoader / 管线脚本 / 测试 / 文档。7 层任何一层 bug 都会让这个 PR 卡评审。MVP solo 开发也许"卡了就 force push"，但日后真有 reviewer 时这个 PR 不可能 merge。

更稳的是拆：

- PR-A：migration 007 + drift v12 + manifest API（基础设施，不接学习页）
- PR-B：pipeline.py 单一入口 + 一次完整 publish dry-run（验证管线）
- PR-C：WordbookLoader 接 manifest 分支，**feature flag 默认关**
- PR-D：feature flag 开 + bundled 改 fallback（默认走 manifest）
- PR-E：30 天后单独 PR 改 fallback 策略（不是直接删，见观察 3）

每个 PR 可独立 revert。这才符合 MVP "高速迭代但每步可回滚"的心态。

## Q4 单选回答

**(A) Phase 0.5，但不是文档说的那个 Phase 0.5。**

理由一句话：作者定义的 Phase 0.5（合脚本 + GC dry-run）是 Phase 1+2 的硬依赖——pipeline.py 没有 publish-manifest 子命令，1+2 跑不通端到端。所以本质上 0.5 不是"先做"，是 1+2 的 PR-B。把它单独立 phase 反而制造拖延空间。

我会把"管线收口 + 状态机实现 + manifest API"打包作 Phase 1+2 的 PR-A/PR-B，**第一周完成**；PR-C/D（客户端改造）作第二周。这比作者的"0.5 天 + 3-4 天"更现实，因为状态机和 manifest 多包一致性（观察 4、5）会吃掉时间。

不是 (B) 的理由：直接做 1+2 不先把管线和状态机拉直，会在客户端调试的时候反复回头改后端，PR-C 卡住。

## Q5 几个根本性盲点（5 年视角）

1. **没有 `stable_id_version` 字段**——算法 5 年内必然要升级（观察 1），现在不留版本号字段，将来 migration 全表重算。
2. **`examples.cn` 应该是 `examples_translations` 表**——加韩日西班牙语翻译时，cn 字段就是个明显债。一开始改便宜，加了上万行例句后改贵。
3. **没有 `review_state` 列**——一人一 LLM 现在够用，5 年必然有审核工作流（draft/pending/approved/rejected）。
4. **manifest API 没有 ETag / Last-Modified 设计**——文档里 `GET /content/manifest` 看起来每次 200 OK 全量返。每次启动都全量查询是 CDN 真钱场景的基本盘问题。
5. **完全没有 metrics / observability 设计**——包下载成功率、audio fetch 命中率、首启首屏延迟、弱网降级触发率，5 年项目没观测性等于黑盒。

这五条里 #1 和 #2 是**便宜现在改、贵以后改**的——建议作者在 v0.3.0 主文档里至少把字段位置占住，即使初版不实现。
