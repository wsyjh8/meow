我按软件工程设计评审，结论偏反方：**v0.2 方向正确，但下一周不该直接做完整“例句 CDN 化”。应该先做一个更小的发布系统收口：内容包生成、manifest 激活、校验、回滚、GC 的最小闭环。**

文档里当前事实很清楚：App 例句文本来自 bundled JSON，不来自 API；音频则已走远端 fetch + 本地缓存；例句文本更新要重新 build APK，而音频更新可分钟级生效；当前 examples 约 10140 行、音频 ready 2263 行，覆盖率 22.3%，且已有 6932 个 stale MP3。

## 总体判断

v0.2 的大方向是对的：
**静态内容应该被当作“可发布、可校验、可回滚的内容包”，而不是散落在 APK、CDN mock、PG 表和脚本输出之间。** 这一点比“例句 CDN 化”本身更重要。

但方案现在有一个设计重心偏差：它把问题描述成“例句文本是否搬 CDN”，而我认为真正的问题是：

> 你还没有一个可靠的内容发布事务模型。

也就是说，manifest、examples package、audio_assets、CDN 文件、客户端本地导入状态之间，缺少一个明确的 **release unit**。如果只做 `content_manifest active=true`，容易出现“某个包 active 了，但音频、例句、客户端本地状态、回滚策略不同步”的半发布状态。

## Q1：A.4 里哪个判断错了？漏了什么更严重的问题？

A.4 的 5 个问题基本都成立，但“问题 4：例句和音频完整度不一致”不应被当成架构问题本身。例句有 100%，音频只有 22.3%，在 MVP 是合理降级；只要 UI 隐藏喇叭、不影响学习主流程，就不是系统性缺陷。文档本身也把“内容缺失 ≠ 学习失败”列成边界规则，这是对的。

漏掉的更严重问题是：**客户端本地内容的删除、回滚、去污能力没有讲清楚。**

例句包下载并导入 SQLite 后，如果下一版删除某条例句、撤回敏感内容、修复错误包，客户端怎么处理？

仅有 `content_package_state` 记录“imported / failed”不够。还需要至少明确：

1. 每条本地 example 属于哪个 `package_id` / `content_version`。
2. 新包导入是全量替换、增量 upsert，还是 diff patch。
3. `status=deleted/deprecated` 是否会下发到包内。
4. 服务端 rollback 后，客户端是否允许降级或 revoke 本地已导入内容。
5. 导入失败发生在中途时，是事务回滚，还是会留下半包数据。

这比 APK 大 5.6 MB 更关键。5.6 MB 是体积问题；**坏内容无法撤回、半包导入污染本地库，是内容系统的可信性问题。**

## Q2：删掉 `example_book_memberships` 是否过度精简？

我选 **C：折中，保留 schema 设计，但不立即建表。**

不立即建表是对的。当前没有真实产品需求，直接引入 `example_book_memberships` 会让例句读取路径、生产管线、运营录入都复杂化。文档里说当前用 `examples.word_id` 单挂模型已够，这个判断合理。

但我不建议把它从长期设计里“删除”到只剩一句“未来再加”。因为按词书区分例句难度并不是边缘需求。CET-4、考研、IELTS 对同一个词的例句难度、语域、中文解释粒度确实可能不同。

建议现在这样处理：

```text
v1 物理表：不建 example_book_memberships
v1 包生成：examples 按 word_id 被词书间复用
v1 设计文档：保留 example_book_memberships 作为 future extension point
v1 代码边界：不要把“一个 word 的所有 examples 永远全局共享”写死
```

尤其是包生成器不要假设 `examples.word_id -> 所有词书同一套例句` 是永久真理。可以先用当前查询实现，但接口层命名成“resolve examples for book”，而不是“get global examples by word only”。

## Q3：Phase 1 + Phase 2 合并是否合理？

我选 **B：应分开，但不是恢复旧 Phase 1。**

文档说 memberships 已 done，所以单独做原 Phase 1 没意义，这点我同意。
但把“DB migration + API manifest + pipeline + mobile downloader + checksum + fallback + import + 测试”塞进一个 3-4 天 Phase，风险偏大。

我建议重新定义 Phase 1：

```text
Phase 1：Content Release Core
- content_manifest 状态模型补齐：active / deprecated / revoked
- package_id / release_id / supersedes_id / activated_at / expires_at
- pipeline 能 build examples package
- pipeline 能 validate checksum
- pipeline 能 publish 到 manifest
- gc-stale dry-run
- 不改 mobile 读取路径
```

然后 Phase 2 再做 mobile manifest-driven import。

这样第一步能验证“发布系统是否可信”，而不是一口气改到客户端运行时。对 solo 开发尤其重要：小 PR、小回滚面、小测试矩阵。

## Q4：下一周单选推荐

我选 **A：Phase 0.5 管线收口，但要升级成“内容发布最小闭环”，不是只合脚本 + GC。**

一句话理由：**当前最大风险不是例句还在 APK，而是内容生产、manifest、音频、stale GC、校验和回滚没有形成一个可靠发布单元；先把发布系统做稳，后面 CDN 化才不会把复杂度扩散到 mobile。**

建议 5 天拆法：

```text
Day 1：统一 pipeline.py 入口，保留原脚本兼容 wrapper
Day 2：build-examples-package + checksum + manifest dry-run
Day 3：publish-manifest 支持 active/deprecated/revoked/supersedes_id
Day 4：gc-stale dry-run + 删除报告 + grace window
Day 5：端到端 release gate 测试：生成包、校验、激活、回滚、GC 预演
```

这周先不碰 LearningPage，不碰 FSRS，不碰 rewards，不移除 bundled fallback。

## Q5：长期 5 年视角的根本性误区

最大误区是：**把 stable_id 当成内容治理的核心，而不是把 release/version/audit 当成核心。**

stable_id 解决的是“引用稳定性”；它不解决：

* 哪一批内容一起发布；
* 哪个版本正在服务用户；
* 哪个版本可回滚；
* 哪个版本被撤回；
* 客户端本地是否导入了坏包；
* 删除/更正是否真正传播到设备；
* 内容来源、审核、生成器、TTS 模型、人工修改记录如何追溯。

所以长期架构里应该引入一个更明确的概念：

```text
content_release
- release_id
- package_kind
- book_id / scope
- version
- status: draft / validated / active / deprecated / revoked
- artifact checksum
- generated_by
- reviewed_by
- activated_at
- revoked_at
- rollback_to_release_id
```

`content_manifest` 可以是面向客户端的分发表，但后台治理上最好有 `content_release` 作为事实 owner。否则 5 年后你会得到很多稳定 ID，但不知道“哪批内容为什么、何时、由谁发布给了哪些用户”。

最终建议：**v0.2 不要推翻，但要降一档执行。先做发布系统核心，再做例句 CDN 化。**
